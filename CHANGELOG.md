# Catalog Changelog

High-level, user-facing catalog changes by month: new templates and notable version updates, one line each. Feeds the marketplace "What's New" section. Maintained by the template pipeline at ship time (entry added when a template or version merges); internal tooling changes are not listed.

## 2026-08

- **New template: cpln-advisor 1.0.0** — watches the workloads in your own org and turns their metrics, logs and billed cost into LLM-generated tuning suggestions, with an optional Autopilot that applies the qualifying ones and keeps a one-click revert for each
- **pgedge 2.0.0** — **replication never actually worked.** PostgreSQL 17.11 refuses to create a Spock replication slot unless the plugin is allow-listed, so every node accepted writes that never left it while reporting healthy — if you run 1.x, your cluster is almost certainly not replicating, and the README has a one-command fix you can apply without upgrading. Also fixed: restarting every node at once used to destroy the mesh permanently, a backup schedule starting with `*` broke the install, a single-node cluster could not serve reads, and `pgcat.maxClientConn` never did anything. **This release no longer creates a GVC** — it deploys into one you already have. **Do not `helm upgrade` a 1.x release onto it**: migrate to a new release instead, because a chart that stops declaring a GVC makes Helm delete it and everything inside it
- **coraza 1.2.1** — the startup hook that configures the WAF's reverse proxy **never actually waited** for the proxy to be ready, so a configuration that failed to apply was reported as a healthy WAF that was not inspecting traffic. The hook now waits, verifies, and refuses to serve if it cannot configure itself, and failures say why in `cpln logs`. The bundled rule set moves from CRS 4.7.0 to 4.28.0, and request-body inspection is properly sized — the old defaults returned 504 for any body over 50 KB, against roughly 1.8 MB now. Pin a digest or a datecode, never a moving tag like `-lts`; only the Caddy image variants work
- **New template: pgvector 1.0.0** — PostgreSQL 18 with the pgvector extension for vector similarity search: embeddings, distance operators, and both `hnsw` and `ivfflat` indexes, created for you at first boot. Optional PgBouncer pooling and scheduled backups to S3, GCS or MinIO. Note that in PgBouncer's default `transaction` pool mode a plain `SET hnsw.ef_search` leaks between clients — set it inside a transaction with `SET LOCAL`, or use `poolMode: session`
- **redis 3.7.0**, **redis-cluster 1.6.0**, **redis-multi-location 2.2.0** — all three can now run **Valkey** instead of Redis via a new `engine` value. Valkey is the BSD-3-Clause fork of Redis 7.2 with no paid edition, so nothing is feature-gated. Redis stays the default and an install that does not set `engine` is unchanged. The engine is an install-time choice: switching a running release is not supported, because the two write different on-disk formats
- **redis-cluster 1.6.0** also fixes three defects that predate this release. `port` never worked — any non-default value crash-looped every node, because the health check and the cluster bus both assumed 6379. A password-protected cluster reported healthy even with the **wrong password**, since the health check accepted any reply rather than requiring a valid one. And a transient DNS hiccup during first boot restarted nodes instead of being retried, which could cost several restarts and around twenty minutes before a cluster formed
- **New template: guacamole 1.0.0** — clientless remote desktop gateway: RDP, VNC and SSH in the browser with no client install and no VPN, backed by bundled PostgreSQL for users, connections and session history. The admin account is a secret you create before installing, replacing Guacamole's well-known default login before the gateway ever serves a request. Runs as a single instance — an upgrade keeps the endpoint reachable but logs everyone out and ends open desktop sessions
- **New template: searxng 1.0.0** — privacy-respecting metasearch that queries upstream engines and merges the results, with a JSON API (`/search?q=...&format=json`) that gives AI agents web results without an API key or a per-query bill. Private by default, with the bot-detection rate limiter off: the limiter returns 429 to non-browser clients, so turning it on protects a public instance but blocks the agent use case — the README lays out both sides of that choice. The signing key is a secret you create before installing
- **New template: pocketbase 1.0.0** — an entire app backend in one executable: embedded SQLite, an auto-generated REST API over your collections, user auth, file uploads, realtime subscriptions and an admin dashboard, on a persistent volume with scheduled snapshots. Single instance by upstream's design, so every restart is about 85 seconds of downtime. Realtime uses Server-Sent Events, and any one connection is capped at ten minutes — the official SDKs reconnect transparently, a hand-rolled client must handle it. Admin credentials and the encryption key are a secret you create before installing
- **postgres-highly-available 2.7.0** — Patroni's cluster metrics now flow into the built-in metrics stack, so `patroni_primary`, replication streaming state, WAL position, timeline and failsafe status show up in Grafana next to the standard workload metrics. Nothing to configure and no exporter to run. These are cluster-state metrics — who is primary, is replication healthy, did we fail over — not database performance; connection counts and query stats would need a separate exporter this template does not ship
- **postgres-highly-available 2.6.0** — three defects that only show up when you try to restore, plus one that breaks connection pooling. Backups: the base backup was skipped for the first **six hours** of every install (WAL was archiving the whole time, so everything looked healthy while there was nothing to restore against), and the backup sidecar was being killed for running out of memory before it could finish — on Azure and GCS that meant **no base backup at all, silently**. Connection pooling: any database password containing a double quote broke *every* PgBouncer login, because the credential was written into PgBouncer's user list unescaped. Failover: the consensus timeouts were an invalid combination that Patroni silently rewrote, so a cluster configured to tolerate a 30-second etcd outage actually gave up after 14 and demoted a healthy primary. The cluster now also keeps serving through an etcd outage instead of failing over, when every member is still reachable. **Upgrading does not change a running cluster's timeouts** — they were written to etcd when it was created; the README gives the one `patronictl` command to move an existing cluster
- **timescaledb-highly-available 1.2.0** — the same failover, credential-escaping and backup-memory fixes as `postgres-highly-available` 2.6.0 above, and the same note applies: upgrading does not retune a cluster that already exists
- **postgres-multi-location 1.1.0** — ~~failover timings brought in line with the other two Patroni templates~~ **Correction (2026-08-30): this change never shipped.** 1.0.x, 1.1.0 and 2.0.0 all ship the same `ttl: 45` / `loop_wait: 10` / `retry_timeout: 15`, which is a valid combination Patroni honours as written. No cluster is misconfigured and no action is needed; the README now explains how to widen the tolerance yourself if your etcd quorum spans regions
- **clickhouse 2.8.0** — the Azure Storage account key was still a plain template value, so it landed in your Helm release and in a stored config file. It is now a secret you create before installing, like the GCS and Hetzner credentials already were
- **clickhouse 2.7.0** — the GCS and Hetzner object-storage credentials were template values; both are now secrets you create before installing
- **debezium-server 1.2.0** — every credential the connector uses — the source database, the offset and schema-history stores, all six sink types and the schema registry — was a plain value that ended up in your Helm release. They are now keys in one secret you create before installing; which keys you need depends on your source and sink, and the README lists them per combination. Five settings that were previously inferred from a credential being non-empty now have explicit switches
- **prometheus 1.2.0**, **thanos 1.2.0**, **mimir 1.2.0** — the MinIO object-storage credentials were template values; they are now one secret you create before installing
- **timescaledb 1.2.0** — the MinIO backup credentials were template values; they are now a secret you create before installing
- **uptime-kuma 1.2.0** — the dashboard is no longer published to the internet by default. Uptime Kuma has no password setting: the admin account belongs to whoever opens the setup wizard first, so an exposed install could be claimed by a stranger. Create the account over `cpln port-forward`, then turn public access on if you want public status pages — the README has the sequence
- **airflow 1.5.0** — the key that encrypts your stored Connection credentials, the API token signing key and the admin password were all template values defaulting to `CHANGE_ME`, published in this repository. They are now one secret you create before installing, and the web UI is no longer reachable from the internet by default (reach it with `cpln port-forward`, or open it deliberately). **The encryption key cannot be rotated** — if you carried the default forward, every Connection you saved is encrypted under a publicly-known key and must be re-entered after changing it. Two settings that never did anything were also removed, and a wide task fan-out is known to lose roughly a third of its tasks to an upstream bug — see the README before relying on large bursts
- **gitea 1.1.0** — the first admin login and the three long-lived signing keys were template values used exactly as written. All four are now one secret you create before installing. The signing keys cannot be rotated safely — changing `SECRET_KEY` makes existing two-factor enrolments and tokens unreadable — so treat the published defaults as compromised and plan a migration rather than a simple upgrade. The setup instructions no longer require the `gitea` binary you do not have
- **glitchtip 1.1.0** — the session signing key and the admin login were template values used as written; both are now one secret you create before installing. Rotating the signing key logs everyone out, so treat the old default as compromised. Also documents that a fresh highly-available install takes around six minutes to settle, with the worker restarting throughout — that is expected, not a failure
- **redpanda 1.1.0** — the Kafka superuser password was a template value, and the management console was published to the internet **with no login at all**: console authentication is a paid feature, so the free build shares one session that carries superuser access. The console is now internal by default (reach it with `cpln port-forward`), and the superuser credentials are a secret you create before installing. Topic data now gets scheduled snapshots. Note the broker admin API remains unauthenticated to anything inside your GVC, for reads **and** writes
- **cpln-task-runner 1.3.0** — the admin API key defaulted to empty, which disables admin authentication entirely, while the API was published to the internet — so client and tier management was open to anyone. The key is now a secret you create before installing, and an install cannot be public without one. Public access now defaults to off, because task submission itself has **no authentication**: an unknown client ID is accepted and registered automatically, so an open endpoint lets anyone drive your workers
- **keycloak 1.1.0** — the bootstrap admin password was a template value used as written; it is now a secret you create before installing. Keycloak stays reachable from the internet, since applications authenticate against it
- **metabase 1.1.0** — the admin login was a template value used as written; it is now a secret you create before installing. The template also checks at startup that the password does not contain characters that would break Metabase's first-boot setup, and tells you plainly instead of failing obscurely
- **listmonk 1.1.0** — the admin login was a template value used as written; it is now a secret you create before installing. The template also enforces Listmonk's own minimum lengths at startup: previously a too-short value made the installer retry forever behind a `waiting for database` message that blamed the wrong component
- **unleash 1.1.0** — the admin login was a template value used as written; it is now a secret you create before installing. Unleash also now waits for its database before starting, instead of failing its migration for several minutes while a highly-available database elects a leader
- **n8n 1.1.0** — the instance owner login was a template value used as written; it is now a secret you create before installing, holding a password hash rather than a password. **Note n8n re-applies the owner from configuration on every restart**, so hash the password you are already using — hashing a new one during the upgrade will change your own login
- **sftpgo 1.1.0** — the administrator login was a template value used as written; it is now a secret you create before installing. Reach the web admin with `cpln port-forward` — the previous instructions pointed at an address that does not serve it. Note that SFTP user passwords and object-storage keys are still template values: SFTPGo reads them from a file it does not expand variables in, so prefer public-key users, and see the README
- **cpln-trivy 1.2.0** — the token protecting report uploads was a template value (`changeme`) published in this repository, and the endpoint it protects is reachable from the internet — so anyone could publish content into your bucket and have it served. It is now a secret you create before installing
- **postgres 3.4.0** — the database username, password and database name were template values, with a default password of literally `password` shared by every install that did not change it. They are now one secret you create before installing, referenced by `config.credentialsSecretName`, and the chart no longer creates a credentials secret of its own. The backup identity also stopped requesting AWS-wide read access it never used, and `backup.schedule` now accepts `*/15`-style cron expressions, which previously failed to install at all. **If you set `config.username`, `config.password` or `config.database`, the upgrade stops with a message naming the replacement** — read the old values out of your existing `RELEASE_NAME-pg-config` secret before upgrading, because the chart stops creating it (3.4.1 clarifies that message for templates that bundle Postgres)
- **umami 1.2.0** — updates the bundled PostgreSQL to 3.4.0. Umami now creates the database credentials secret for you, so nothing changes in how you configure it; the database settings simply moved from `postgres.config` to `postgres.credentials`. **If you set those values, the upgrade stops with a message naming the replacement.** Give each umami release its own `postgres.config.credentialsSecretName` if you run more than one in an org
- **minio 1.3.0** — the root username and password were template values, defaulting to a working pair published in this repository. Because MinIO is object storage, those are the S3 access key and secret key you put into every client and every other template's backup settings — they are now one secret you create before installing. Note that rotating them takes roughly eleven minutes of mixed old/new state as replicas restart one at a time, so plan it as a maintenance window
- **rabbitmq 1.2.0** — the default user and password were template values (`user` / `changeMe`), and they are the AMQP credentials every producer and consumer puts in its connection string. They are now a secret you create before installing. Two settings that previously did nothing were also fixed: `diskCapacity` was ignored, so a larger volume silently stayed at 10 GiB, and `timeoutSeconds` was ignored in favour of a hardcoded 5
- **pgdog 1.1.0** — each pooled user's password and the admin database password were template values, defaulting to working credentials published in this repository. Each user now names its own secret, and the admin password is a separate one, so an application given a pooled user's credentials cannot also reach the admin database. A user entry can point at the same secret your `postgres` install already uses
- **seaweedfs 1.1.0** — the admin UI username and password were template values, used exactly as written unless you changed them. They are now a secret you create before installing. The S3 credentials were already handled this way and are unchanged
- **weaviate 1.1.0** — earlier versions shipped a working API key as a template value, published in this repository and shared by every install that did not change it; it is the only authentication Weaviate has, so anyone holding it could read and write every collection. The key is now a secret you create before installing, and the OpenAI, Anthropic, Cohere and HuggingFace keys for the AI modules are secrets too, instead of values that ended up in your Helm release. Two long-standing limitations were also confirmed and documented: restarting a 3-replica cluster can leave one replica permanently outside it while still reporting healthy, and supplying a provider key activates that provider whether or not you list it in `modules.enabled`
- **mongodb-cluster 1.1.0** — earlier versions shipped a working database password and a working replica-set keyfile as template values, both published in this repository. The keyfile is what authenticates cluster members to each other, so anyone holding it could join a member to your cluster. Both are now secrets you create before installing, kept separate so an application granted the database credentials cannot also obtain the cluster key. Note the keyfile must be generated with `openssl rand -base64 756` — MongoDB accepts only base64 characters, so a hand-written passphrase will not start the cluster
- **manticore 2.1.0** — the scheduled backup now works: on every earlier version it failed on every run and nothing ever reached your bucket, so an install with backups enabled had none. Restore is available through the orchestrator API. The bearer token that authenticates the cluster is now a secret you create before installing rather than a value shipped in the template, the management UI is internal by default (it has no login of its own, so anyone who could reach it held full admin), and the documented S3 permissions no longer ask for write access on your own source data bucket, which was never needed
- **langfuse 1.1.0** — earlier versions shipped working signing and encryption keys as values, shared by every install; the encryption key protects the LLM provider API keys your users store in Langfuse and cannot be rotated once data exists. All key material is now one secret you create before installing, self-service registration is closed with the owner account provisioned at boot, Google Cloud Storage credentials are a secret rather than values, and session cookies are now marked `Secure` on a public instance
- **open-webui 1.1.0** — the chat UI was published to the internet by default with open registration, and the first person to register became the administrator, so an unclaimed admin account sat on a public URL. The UI is now private by default and sign-ups are closed (the first account is still allowed, so you can claim admin), and the session signing key is a secret you create before installing
- **umami 1.1.0** — the analytics dashboard was published to the internet by default while Umami seeds a fixed `admin` / `umami` login that cannot be overridden, so every install stood on a public URL with published credentials. The dashboard is now private by default: reach it with `cpln port-forward`, change the password, then turn public access on for tracking. The key that signs sessions is now a secret you create before installing
- **mysql 1.5.0** — earlier versions shipped working default passwords (`root-password` and `password`, shared by every install) and turned on a phpMyAdmin console that was published to the internet with no way to close it. Database credentials are now two secrets you create before installing, phpMyAdmin is off by default and internal-only when enabled, and its image is pinned instead of tracking `latest`
- **mariadb 1.4.0** — earlier versions shipped working default passwords (`root-password` and `password`, shared by every install) and turned on a phpMyAdmin console that was published to the internet with no way to close it. Database credentials are now two secrets you create before installing, phpMyAdmin is off by default and internal-only when enabled, and its image is pinned instead of tracking `latest`
- **tyk 1.3.0** — earlier versions published the gateway to the internet by default with a well-known admin key (`mysecret`) that let anyone mint API keys for every API behind it, and never mentioned it in the README. The gateway is now internal by default, the admin key is a secret you create before installing, and keys created without explicit access rights no longer reach every API
- **New template: grafana-multi-location 1.0.0** — Grafana running in several locations against one stretched PostgreSQL cluster, so dashboards, users and data sources are shared everywhere and a region can be lost without losing the service
- **grafana 1.2.0** — the admin password and the encryption key are now user-created secrets referenced by name, instead of values (create them before installing or upgrading), and Grafana's own resource limits are named `maxCpu`/`maxMemory`
- **New template: postgres-multi-location 1.0.0** — one PostgreSQL cluster stretched across regions: a single primary, asynchronous replicas elsewhere, and automatic promotion of a replica in a surviving region when the primary's region is lost
- **postgres-multi-location 1.0.1** — Google Cloud Storage backups now work; at the previous default they ran out of memory and failed with no log output, so backups appeared configured but never completed
- **postgres-multi-location 1.0.2** — `primaryLocation` now places the primary where you ask it on a fresh install, instead of only biasing later failovers. Resource names also dropped the `-ml` infix: **this affects fresh installs only** — back up before upgrading an existing deployment, because the upgrade deletes the volume set holding your data, and see the template README first
- **New template: etcd-multi-location 1.0.0** — stretched etcd cluster with one member per location, for cross-region coordination and as the consensus store behind postgres-multi-location
- **etcd-multi-location 1.0.1** — a fresh install no longer shows configuration drift against its own manifest
- **New template: duckdb 1.0.0** — scheduled SQL analytics over Parquet, CSV and JSON in object storage, run as a cron job that starts, transforms and exits (no always-on server)
- **New template: polaris 1.0.0** — Apache Iceberg REST catalog, letting Trino and other engines share governed lakehouse tables backed by S3-compatible storage
- **New template: meilisearch 1.0.0** — fast, typo-tolerant search engine with instant indexing and a simple REST API
- **New template: nocodb 1.0.0** — no-code database and spreadsheet UI over PostgreSQL, with REST and GraphQL APIs and horizontal scaling (`replicas`)
- **tidb 1.7.0** — TiDB v8.5.7 across the cluster and the backup image; GCS backups now work (they previously failed on every attempt), development-mode installs now reach ready, and region-aware data placement is applied for the first time
- **prometheus 1.1.0** — the built-in Prometheus web UI (expression browser, targets, alerts) is now documented with its internal endpoint, and resource knobs are named `minCpu`/`maxCpu`/`minMemory`/`maxMemory`
- **otel-collector 1.2.1** — installing with public ingestion but no authentication now fails immediately with an explanation and the three ways to resolve it, instead of quietly publishing an open OTLP endpoint
- **otel-collector 1.2.2** — an unsubstituted placeholder left in the metrics endpoint is now rejected at install instead of being accepted and silently dropping every metric, and the collector's workload, identity, policy and secret now describe themselves in the console instead of showing a blank or their own name

- **New template: seaweedfs 1.0.0** — S3-compatible object storage usable as the backup and attachment target for any catalog template that speaks S3
- **New template: trino 1.0.0** — distributed SQL engine that answers a single query across PostgreSQL, MySQL, ClickHouse, MongoDB and more, with a scalable worker tier

- **New template: twenty 1.0.0** — open-source CRM with a customizable data model, REST and GraphQL APIs, and a background worker for automations

- **New template: openbao 1.0.0** — OpenBao secrets engine (Vault-compatible: KV, dynamic secrets, PKI, transit) on raft storage, with auto-unseal via a static key or AWS/GCP KMS

- **supabase 1.1.0** — the API keys, database password, dashboard password and JWT signing secret are now user-created secrets you reference by name, instead of shared defaults published in this repository; the dashboard gains a real login, the public API key can no longer reach admin endpoints, and Realtime subscriptions and S3-compatible storage now work
- **Fourteen templates now pick up the etcd storage fix** — `cdc-pipeline` 1.0.2, `chatwoot` 1.0.1, `glitchtip` 1.0.1, `grafana` 1.2.1, `keycloak` 1.0.1, `listmonk` 1.0.1, `metabase` 1.0.1, `n8n` 1.0.1, `nocodb` 1.0.1, `polaris` 1.0.1, `temporal` 1.0.1, `twenty` 1.0.1, `umami` 1.0.1 and `unleash` 1.0.1 all bundle highly-available PostgreSQL, whose coordination store could fill its storage and force the database read-only after a couple of months. **Upgrade if you are running the highly-available database option — it is the DEFAULT in `chatwoot`, `glitchtip`, `grafana`, `keycloak`, `metabase`, `n8n`, `temporal` and `unleash`, so most installs of those are affected even if you never changed a setting.** In `listmonk`, `nocodb`, `polaris`, `twenty` and `umami` it is off by default. `cdc-pipeline` always bundles it with no way to opt out, so every install of that template is affected
- **postgres-multi-location 1.0.3** — the stretched etcd cluster's history-compaction and storage-quota settings are now configurable, and documented alongside the symptom they prevent
- **postgres-highly-available 2.4.2** — picks up the etcd fix below: the coordination store no longer fills its storage and forces the cluster read-only after a couple of months. **Upgrade if you are running any earlier version**
- **timescaledb-highly-available 1.0.1** — picks up the same etcd fix; earlier versions are affected the same way
- **etcd 1.4.2** — etcd now trims its own history automatically, so its storage no longer grows without limit and fill up the default 2 GiB after a couple of months, at which point the cluster went read-only and any database using it for coordination could start restart-looping. - **etcd-multi-location 1.0.2** — history retention and the storage quota are now configurable; behaviour at the defaults is unchanged
- **grafana-multi-location 1.1.1** — the Redis that coordinates alerting HA is now unauthenticated by default, so turning HA on needs no extra secrets (passwords remain available as an option), and the stretched etcd cluster's compaction settings are configurable
- **grafana-multi-location 1.1.0** — alerting can now keep running when a region is lost: set `alerting.highAvailability.enabled` and every location evaluates alert rules, with a stretched Redis making sure a notification is still sent only once. Alerting can also be turned off entirely with `alerting.enabled`
- **grafana-multi-location 1.1.1** — turning on alerting HA no longer requires creating any extra secrets; the coordinating Redis is unauthenticated by default and can be given passwords when you want them
- **dbeaver 1.3.0** — the database console is no longer published to the internet by default, and no longer ships with a known admin password. Earlier versions installed with the password `Password123` on a login form open to the whole internet, with no way to close it. The admin password is now a secret you create before installing (`admin.passwordSecretName`), and public access is an explicit `publicAccess.enabled` choice, off by default. **If you are running any earlier version, treat its admin password as compromised**
