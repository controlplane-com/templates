# Chatwoot — Maintainer Briefing

## What it is
- Open-source customer-engagement platform: live-chat widget, shared email inbox, omni-channel agent desk (the self-hosted Intercom/Zendesk alternative). Ruby on Rails + Sidekiq.
- License: MIT core. We ship the **Community Edition** image (`-ce` tag), which omits the separately-licensed enterprise code — no key, registration, or activation. SSO/SAML, audit logs, agent capacity, custom branding, SLA policies and Captain AI are absent by design.

## Common use cases
- Website live-chat widget backed by a real agent inbox, self-hosted so conversation data stays in the customer's own infrastructure.
- Shared team inbox for support email, with assignment, labels and canned responses.
- A support desk alongside other catalog templates — listmonk for outbound campaigns, docmost for internal knowledge, minio for attachments.
- Compliance-driven support where no third-party SaaS may hold the conversations.

## Architecture on cpln
| Resource | Purpose |
|---|---|
| `{release}-chatwoot` (stateful, :3000, `chatwoot.replicas`) | Puma — dashboard, API, chat widget, ActionCable `/cable`; readiness `/api` (Postgres + Redis), liveness `/health` |
| `{release}-chatwoot-worker` (standard, fixed 1 replica) | Sidekiq; **also runs `db:chatwoot_prepare` migrations + the first-run onboarding bootstrap on every boot**. No probes |
| `{release}-chatwoot-redis` (stateful, fixed 1, :6379) | `redis:8`, AOF + `noeviction` + `requirepass` — Sidekiq queues, ActionCable pub/sub, cache, install-onboarding flag |
| `{release}-postgres-ha` + `-etcd` + `-postgres-ha-proxy` (postgres-highly-available 2.5.0, **default**) | 3 Patroni replicas on PostgreSQL 17.5 + 3 etcd + HAProxy leader endpoint; its image ships **pgvector natively** |
| `{release}-postgres` (postgres 3.4.1, opt-in) | single-instance dev path on `pgvector/pgvector:pg18` |
| DB credentials secret (dictionary, **user-created** since 1.3.0) | `username`/`password`/`database` — named by `postgresHA.config.credentialsSecretName` (HA) or `postgres.config.credentialsSecretName` (single); the active subchart initializes from it and Chatwoot's `POSTGRES_DATABASE`/`USERNAME`/`PASSWORD` env vars read it. `{release}-postgres-config` holds only backup bucket/region, and only when HA backups are on |
| Volumesets ×2 | `-chatwoot-redis-vs` (AOF at `/data`) + `-chatwoot-storage` (`/app/storage`, rendered only in `local` mode) |
| web-start + worker-start secrets, identity, policy | the two start scripts; `reveal` on exactly those plus the user's three prerequisite secrets by name (app keys, DB credentials, Redis password) (and the s3-compatible/SMTP secrets when set); AWS cloud-account link in keyless S3 mode |

- Both app workloads run the **same image**; it declares no ENTRYPOINT/CMD, so each mounts its own start script.
- The web workload is `stateful` in **every** storage mode — workload type is immutable on the platform, so this is what makes a `local → object storage` upgrade possible.
- Default render = 23 resources (1.2.1 was 24; the chart-created DB secret is gone). No GVC created.

Prerequisite secrets (create BEFORE install; verbatim from the shipped README, the DB one executed 2026-10-14):
```bash
cpln secret create-dictionary --name my-chatwoot-db-credentials \
  --entry username=chatwoot \
  --entry password="$(openssl rand -hex 24)" \
  --entry database=chatwoot
cpln secret create-dictionary --name my-chatwoot-secrets \
  --entry SECRET_KEY_BASE="$(openssl rand -hex 64)" \
  --entry ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY="$(openssl rand -hex 16)" \
  --entry ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY="$(openssl rand -hex 16)" \
  --entry ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT="$(openssl rand -hex 16)"
```
(SMTP and s3-compatible keys use the same `cpln secret create-dictionary --name X --entry K=V` form.)

## Availability posture
- **Multi-replica WEB is supported and shipped** — `chatwoot.replicas` defaults to the proven 1; `>1` is a real HA tier (token/cookie sessions, broadcasts fan out through the shared Redis, no sticky sessions) and requires object storage.
- Measured at 2 replicas: cross-replica ActionCable fan-out proven deterministically (a broadcast published from **each** replica in turn reached one socket served by one replica); web-only rolling restart **558/560, zero 5xx** (two client-side resets in a 6 s window); hard replica kill **200/200**.
- **Worker is fixed at 1** (it owns migrations) and **Redis is fixed at 1** (pub/sub); scale background throughput with `worker.concurrency`.
- A full `helm upgrade` is NOT zero-downtime — see the Redis bullets below.

## Troubleshooting / considerations
- **After ANY restart of the bundled Redis, restart the `{release}-chatwoot` web workload or live updates stay dead — silently.** Sidekiq, cache and `/api` recover on their own, but Rails' ActionCable subscriber connection never re-establishes: `pubsub channels` is empty, new sockets get `welcome` and then nothing, and **the web log prints nothing** while `/api` stays green. Reproduced on both test releases, permanent until restarted; a force-redeployment fixed it (~209 s to ready). Upstream Rails/Chatwoot behavior, not template code.
- **`helm upgrade` restarts Redis even when no redis value changed, and the web readiness probe (`/api`) 500s while Redis is down — so every replica leaves the load balancer.** Measured on the 2-replica release: **178 non-2xx of 562 requests (31.7%)** over a ~3-minute window (503×113, 500×65). A web-only force-redeployment does not touch Redis and is clean. Self-heals fully; tell users to upgrade in a quiet window.
- **Redis is single-node by design, not by convenience.** Chatwoot's `config/cable.yml` builds its own connection from `REDIS_URL`/`REDIS_PASSWORD` and has **no Sentinel support** — the spec's "Chatwoot is Sentinel-aware" premise was false and the in-catalog `redis` (Sentinel) subchart was dropped after round 1, where every ActionCable broadcast died on `getaddrinfo: Name does not resolve (redis://mymaster:6379)`. Redis also does not propagate pub/sub between replicas, so a second node would silently drop a share of broadcasts. Never "upgrade" this to a replicated Redis.
- **The database mode is INSTALL-TIME ONLY.** Flipping `postgresHA.enabled`/`postgres.enabled` on a live release points Chatwoot at a different, empty database (separate volumeset, different major: 17.5 HA vs 18 single) — onboarding re-runs and the old data is orphaned, not migrated. The chart fails the render if both or neither is enabled.
- **pgvector is mandatory** — the schema runs `CREATE EXTENSION "vector"`. The HA image has it natively (that is why HA is the default); the single-instance path is guarded by a render check on a `postgres:`-prefixed image. Known heuristic gap: `docker.io/library/postgres:18` slips through (accepted in review).
- **First HA install takes ~8 minutes and the worker crash-loops on the way there — both are expected.** Measured 486 s to all-ready; the worker restarts ~5–7 times on `PG::ConnectionBad` until Patroni elects a leader, each dumping a full Rails backtrace. The web readiness budget is `10 + 25×20 = 510 s` and this run consumed **443 s (87%)** — `failureThreshold` is already at the platform maximum of 20, so any further widening must come from `periodSeconds`. Single-instance postgres path: 205 s.
- **The worker reports `ready: true` while crash-looping** (no probes) — worker readiness is not a health signal, and a failing migration surfaces as "web never becomes ready" (the web start script gates on the `accounts` table). Read the worker logs.
- **`storage.type: local` is an evaluation shape.** A volumeset cannot be shared, so the worker has no `/app/storage` at all — attachment emails and ActiveStorage analyze/purge jobs cannot succeed. It is also the hard blocker for `replicas > 1`.
- **`storage.s3Compatible.endpoint` must be reachable by the END USER's browser.** ActiveStorage serves blobs by 302-redirecting the client to the storage endpoint, so an in-GVC-only MinIO address makes attachments look broken from a laptop even though the round trip works inside the GVC.
- **AWS S3 is keyless only** — the identity carries `cloudAccountLink` + `policyRefs: [cpln-connector, {policyName}]` and the Ruby `aws-sdk-s3` picks it up via `Aws::InstanceProfileCredentials` (no `AWS_ACCESS_KEY_ID` in the container). Static keys work only for `s3-compatible`, which also requires `endpoint`.
- **With SMTP off, mail does not go missing — it raises** (Chatwoot falls back to `sendmail`, absent from the image). Fine for a trial; configure SMTP before inviting agents. **Rotating any of the four prerequisite keys is destructive**: `SECRET_KEY_BASE` logs out every user, the three `ACTIVE_RECORD_ENCRYPTION_*` keys make stored 2FA secrets undecryptable (MFA round-trip verified).
- **`signupEnabled` was REMOVED from values** — Chatwoot reads the flag from the DB-backed `installation_configs` table seeded at first install, so the env var did nothing on upgrade. Self-serve signup is toggled post-install at `/super_admin` → Settings → `ENABLE_ACCOUNT_SIGNUP`.
- **1.3.0: the DB credentials became a prerequisite secret (maintainer ruling 2026-10-14, work item 5284).** Rule: when a dependency takes only a credentials-secret NAME, the parent requires the user to create that secret rather than rebuilding it from plaintext values. 1.1.0–1.2.1 kept `postgres.credentials.*` as values under the bundled-plumbing exception and rendered `templates/secret-db.yaml` (now deleted) in both modes, which put the DB password in the Helm release. `postgres.credentials` now fails at render (`chatwoot.validateDatabaseSecret`, mirrored in the wizard). Chatwoot already read user/password/database as discrete `cpln://secret/…` env vars and the two start scripts only use those env vars, so no URL assembly and no character restriction were involved; no render-time check on the old values existed. **Redis followed on 2026-10-16** (maintainer: each datastore gets its own dictionary secret): `redis.auth.password` → `redis.credentialsSecretName` (key `password`), render-refused by `chatwoot.validateRedisSecret`; `{release}-chatwoot-creds` is no longer rendered, so upgrading from 1.2.x deletes it — the user creates a NEW-name secret holding the current `redisPassword` (wizard rule refuses the old name). Rotation: `cpln secret edit` → force-redeploy `-chatwoot-redis`, then `-chatwoot-worker`, then `-chatwoot` (the web restart is needed after any Redis restart anyway). **[UNPROVEN] until the test round:** the 1.2.1 → 1.3.0 upgrade carrying the password over, and the rotation order.
- **Upgrading 1.2.x → 1.3.0 deletes the chart-created DB secret**, because the new chart no longer renders it. The user must create a secret under a NEW name holding the CURRENT credentials (the data dir keeps the password it was initialized with) and point the active mode's `credentialsSecretName` at it. The wizard enforces the new name with a rule keyed on `context.fromVersion < 1.3.0` (verified headlessly: carried name → 1 error, new name → 0, HA, single and defaults). Expect the bundled Postgres to restart (it now reads the new secret) and new workload versions to stall ~10 min on `is not allowed to reveal the secret` (authorization edge cache, measured on gitea 1.3.0) before clearing on their own. **Not yet live-tested on chatwoot.**
- **Both name knobs exist because a parent cannot template a subchart value**: each subchart reads its own `config.credentialsSecretName`; `chatwoot.postgres.secret.name` picks the active one. Secret names are org-wide, so each release needs its own secret.
- **Older upgraders get the subchart's own removal errors** (`postgres.config.username` from postgres 3.4.x, the `postgres` block from pg-ha 2.5.0); their advice — create a dictionary secret — is now correct for chatwoot too.
- **Password rotation (README "Rotating the database password"):** `ALTER ROLE` → `cpln secret edit` → force-redeploy the database and wait → force-redeploy worker then web. The HA step (`{release}-postgres-ha` redeploy) is unverified — pg-ha documents no rotation procedure.
- **Wizard (1.3.0, first descriptor):** imports postgres 3.4.1 (single mode; pooler excluded + yamlOnly, image help overridden for pgvector); pg-ha 2.5.0 has no descriptor, so its keys are parent fields in the Database step behind the virtual `dbMode` chooser. `gvc` limited to 1 location. The `postgresHA.proxy.enabled` mirror can only refuse the key's presence (lint forbids reading an undeclared path), so even an explicit `true` is flagged.
- **MinIO backup keys are a prerequisite dictionary secret on both paths** (`accessKey`/`secretKey`) — `postgres.backup.minio.credentialsSecretName` since postgres 3.4.0 (chatwoot 1.1.0), `postgresHA.backup.minio.credentialsSecretName` since chatwoot 1.2.1 (1.2.0 still shipped the inline keys pg-ha 2.5.0 refuses). Inline keys fail the render.
- Backups verified on the HA path: `postgres-backup:17.1.0` against PostgreSQL 17.5 produced a valid `pg_dumpall` containing this install's live data and `CREATE EXTENSION IF NOT EXISTS vector`.
- **HA password rotation must also update the `repl` role (measured on listmonk 1.6.0, 2026-10-14).** postgres-highly-available 2.5.0 uses the same secret password for its replication user `repl`; after `ALTER ROLE <user>` + secret edit + redeploy, the standbys failed with `password authentication failed for user "repl"` while the app kept working on the leader. `ALTER ROLE repl PASSWORD '<new>'` on the leader restored streaming in ~12 s. README and wizard help say so.
- **HA rotation ORDER matters (spike 2026-10-15, postgres-highly-available 2.5.0, 3/3 pass).** `ALTER` + secret edit + force-redeploy of `-postgres-ha` is NOT safe on its own: the platform restarts members highest ordinal first (2→1→0, observed 5/5, undocumented) and the chart's preStop calls `/switchover` with no candidate, so the leader can hand off to a member still on the OLD password. Measured: a diverged timeline that HAProxy routed clients to (spike), and on chatwoot a replica stuck `forked off` for 19 min while the leader streamed ~16 GB/min to it (~$30 egress, single location). Safe order (README section): switch the leader to `-0` first, ALTER user + `repl` on `-0`, edit the secret, redeploy — `-0` restarts last. Recovery: `POST /reinitialize {"force":true}` on the stuck member. Also: Patroni's DCS config keeps the INSTALL-time password readable unauthenticated at `:8008/config` (survives rotation) — README step 7 PATCHes it out; chart fix + preStop candidate hardening tracked on 5284.
- **1.3.1: HA database image override for CVE-2026-103484 (work item 5376, 2026-10-27).** The vendored postgres-highly-available 2.5.0 defaults to `controlplanecorporation/patroni-postgres:0.7` (pgvector 0.8.0). 1.3.1 sets `postgresHA.image: controlplanecorporation/patroni-postgres:0.8` (pgvector 0.8.7) instead of moving to pg-ha 2.8.1, which was unpublished at the time; move to the subchart version that carries the fix in a later version and drop the override then. `chatwoot.validatePostgresHAImage` (HA mode only) refuses patroni-postgres tags 0.1-0.7 and an empty value (which would fall back to the subchart's 0.7), mirrored by a wizard rule on `postgresHA.image`. The upgrade restarts the Patroni members (unconstrained stateful rollout), giving a brief write interruption while the leader changes; the HAProxy proxy workload does not restart (helm may print `Updated` for it from a tag bump, but its replicas keep running). The app restart is the longer interruption: the single web replica stops before the new one serves (measured ~110 s for the web tier). `ALTER EXTENSION vector UPDATE;` only refreshes the catalog version. Chatwoot's schema creates `vector`, so its database is the one that needs the ALTER. E2E tests onboarded in this version (`chatwoot/tests/`). Not live-tested at build time.
