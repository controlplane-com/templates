# Keycloak — Maintainer Briefing

## What it is
- Open-source identity and access management: single sign-on, OIDC/SAML identity provider, user federation (LDAP/AD), social login, fine-grained authorization. Apache-2.0, CNCF incubating.
- Runs Keycloak 26 in **production mode** (`kc.sh start`, not `start-dev`) against PostgreSQL. Clustered by default over embedded Infinispan.

## Common use cases
- One login across a company's internal apps (the apps become OIDC clients).
- An auth backend for a product: user registry, password reset, MFA, token issuance.
- Bridging an existing LDAP/AD directory into modern OIDC/SAML apps.
- Sitting in front of other catalog templates that speak OIDC (grafana, gitea, unleash…).

## Architecture on cpln
| Resource | Purpose |
|---|---|
| `{release}-keycloak` workload (stateful, :8080 http) | Keycloak server; ports 7800 + 57800 (tcp) added only when `replicas > 1` |
| `{release}-keycloak-startup` secret (opaque) | Boot script: DB wait + cluster advertise-address derivation |
| user's `admin.secretName` secret (dictionary, **prerequisite**) | Bootstrap admin `username` + `password` — created by the user, never by the chart |
| identity + policy | `reveal` on exactly three secrets: admin, startup, DB credentials (two of them user-created, granted by name) |
| user's DB credentials secret (dictionary, **prerequisite** since 1.5.0) | `username`/`password`/`database` for the bundled DB, named by `postgresHA.config.credentialsSecretName` (HA) or `postgres.config.credentialsSecretName` (single). The active subchart initializes from it; Keycloak reads `KC_DB_USERNAME`/`KC_DB_PASSWORD` and `POSTGRES_DB_NAME` (fed into `KC_DB_URL` via `$(VAR)`) from it. 1.2.0–1.4.0 built it from `postgres.credentials.*` (`secret-db.yaml`, deleted in 1.5.0) |
| `postgresHA` subchart (default, **2.5.0** since 1.3.0 — creates no credentials secret; `{release}-postgres-config` holds only backup bucket/region, and only when backups are on) or `postgres` subchart (dev, **3.4.1** since 1.2.0 — creates no secret of its own) | All durable state; exactly one enabled (XOR validated) |

- **No volumeset** — realms, users and sessions all live in Postgres.
- Clustering uses **JGroups JDBC_PING through the shared database** (no UDP gossip, which the platform does not support on internal ports). Each replica advertises `replica-{i}.{workload}.{location}.{gvc}.cpln.local`, derived in the startup script from `$HOSTNAME` — valid only because the tier is `stateful`.

## Key knobs
| Knob | Default | Note |
|---|---|---|
| `image` | `quay.io/keycloak/keycloak:26.6.3` | |
| `replicas` | `2` | 2+ = Infinispan cluster, zero-downtime restarts; 1 = clustering disabled (local cache) |
| `resources` | 1000m/500m cpu · 2Gi/1Gi mem | JVM heap = 70% of the limit; **do not go below 1.5Gi** |
| `admin.secretName` | `my-keycloak-admin` | **Prerequisite dictionary secret** (`username`, `password`) — 1.1.0 |
| `publicAccess.enabled` | `true` | Browsers must reach the login/OIDC endpoints; kept public deliberately |
| `internalAccess.type` | `same-gvc` | `none` is rejected at render when `replicas > 1` |
| `postgresHA.*` / `postgres.*` | HA on, single off | Exactly one; `postgresHA.proxy.enabled` must stay true |
| `postgresHA.config.credentialsSecretName` / `postgres.config.credentialsSecretName` | `my-keycloak-db-credentials` (both) | **REQUIRED prerequisite** dictionary secret (`username`, `password`, `database`) for the store in use, **1.5.0+**; must exist BEFORE install; only the active mode's key matters. `postgres.credentials` (1.2.0–1.4.0) now fails at render |
| `postgresHA.backup.minio.credentialsSecretName` / `postgres.backup.minio.credentialsSecretName` | `my-keycloak-minio-credentials` | genuine prerequisite, only when `backup.provider: minio` (HA since 1.3.0, single since 1.2.0) |

## Troubleshooting / considerations
- **Workload wedged with ZERO log lines** → a prerequisite secret (admin or DB credentials) does not exist. `cpln logs` shows nothing because the container never starts; the only diagnostic is `status.versions[].message` from `cpln workload get-deployments … -o yaml` (**not** plain `get`). Self-heals in ~5.5–10.5 min once the secret exists, or force a redeployment (~90 s).
- **Admin password is first-boot only.** `KC_BOOTSTRAP_ADMIN_*` is consulted only when no admin exists; editing the secret on a live install changes nothing. Change it in the admin console. Same trap as listmonk/unleash/metabase.
- **The bootstrap admin is temporary by design** — Keycloak logs a standing warning until a permanent admin is created and the temporary one removed.
- **Long first boot is normal.** The startup script waits for Postgres by speaking the Postgres SSL handshake (the image ships no `psql`/`pg_isready`/`curl`), and a plain TCP connect is *not* a valid readiness signal — the HAProxy leader endpoint accepts connections before a Patroni primary is routable. HA first boot runs several minutes.
- **Liveness during the DB wait is deliberately suppressed** via the `/tmp/kc-db-wait` sentinel; do not "simplify" the exec probe into an HTTP probe or the workload crash-loops before the database is up.
- **Do not raise `replicas` with `internalAccess.type: none`** — replicas must reach each other on 7800/57800; render-validated.
- **`aws::ReadOnlyAccess`** does not appear on this template's identity, and `postgres` 3.4.1 dropped it in 3.4.0. `postgres-highly-available` 2.5.0 — the DEFAULT store here — still carries it on its identity.
- **1.2.0 adopted postgres 3.4.1, and keycloak absorbed the break rather than passing it on.** 3.4.0 deleted its `{release}-pg-config` secret and now takes only a secret NAME. Because a parent cannot template a subchart value, the name is a plain value (`postgres.config.credentialsSecretName`) that BOTH sides read: keycloak's `secret-db.yaml` renders it, the subchart's env refs and policy consume it, and `keycloak.db.secretName` points the app at it. Net user-visible change is one rename on the single-instance path; **no new prerequisite** at the time (1.2.0–1.4.0) — superseded by 1.5.0, below.
- **The secret name is org-wide, not release-scoped** (forced by the Helm limitation above). Through 1.4.0 the chart owned it, so a second release on the default name was **refused at install** (`managed by a different release`). Since 1.5.0 the user owns it: a second release pointed at the same secret is NOT refused — it would initialize its own database from the same credentials. Give each release its own secret (README says so).
- **A stale 1.1.0 values file fails with the SUBCHART's message, not keycloak's.** Helm renders `charts/…` before `templates/…`, so a parent-side guard would be dead code and was deliberately not added. Since 1.5.0 the subchart's advice — create a dictionary secret yourself — is correct for keycloak too.
- **1.3.0 extended the same absorption to HA** (pg-ha 2.5.0): `postgresHA.postgres.*` was removed, `keycloak.db.secretName`'s HA branch now names the chart-created secret via `postgresHA.config.credentialsSecretName`, and HA MinIO backup keys became a prerequisite secret. From 1.5.0, HA upgraders from 1.2.x put their existing `postgresHA.postgres.*` values unchanged into the prerequisite secret, which is what pg-ha's removal error already tells them.
- **Open (maintainer ruling): the DB-wait gate outlasts the readiness deadline.** `secret-startup.yaml` waits up to 120×5 = 600 s for Postgres, but the derived startup window is ≈ `initialDelaySeconds + 30 × periodSeconds` = `30 + 30×10 ≈ 330 s` (CLAUDE.md's corrected formula), so on a slow first boot the platform restarts the container before the gate's own `did not become ready` message can print (the calcom class in CLAUDE.md). Not changed in place — it is chart logic.
- **1.5.0: the DB credentials became a prerequisite secret (maintainer ruling 2026-10-14, work item 5284).** Rule: when a dependency requires a pre-existing credential secret, the parent requires it too rather than rebuilding it from plaintext values. This retires the "bundled plumbing, nothing for you to create" stance of 1.2.0–1.4.0 above (it put the DB password in the Helm release). `postgres.credentials` now fails at render (`keycloak.validateDatabaseSecret`, mirrored in the wizard; the subchart ignores that key, so the parent guard is live).
- **The JDBC URL is assembled at container start, not at render** (fusionauth 2.5.0 pattern): `KC_DB_URL` is `jdbc:postgresql://{host}:5432/$(POSTGRES_DB_NAME)`, where `POSTGRES_DB_NAME` is a `cpln://secret/….database` env var — deliberately not `KC_*`, so Keycloak never reads it as an option. So the database name must be URL-safe (README prerequisite). Keycloak's own `KC_DB_URL_DATABASE` option would also work and avoid the expansion; `$(VAR)` was kept for consistency with the batch. **Not yet live-tested on keycloak** (proven on fusionauth/plane/langfuse). The startup script reads only the DB host, so it needed no change and its secret (already granted in 1.4.0) stays.
- **Upgrading 1.4.0 → 1.5.0 deletes the chart-created DB secret**, because the new chart no longer renders it. The user must create a secret under a NEW name holding the CURRENT credentials (the data dir keeps the password it was initialized with) and point the active mode's `credentialsSecretName` at it. The wizard enforces the new name with a rule keyed on `context.fromVersion < 1.5.0`. Expect the new workload version to stall ~10 min on `is not allowed to reveal the secret` (authorization edge cache, measured on gitea 1.3.0) and the bundled Postgres to restart (it now reads the new secret). **Not yet live-tested on keycloak.**
- **Rotation:** `ALTER ROLE` first, `cpln secret edit`, force-redeploy the database (`{release}-postgres-ha` or `{release}-postgres`), wait for ready, then force-redeploy `{release}-keycloak`. A rotated `cpln://` reference is never re-resolved by a running replica.
- **Wizard (1.5.0, first descriptor):** imports postgres 3.4.1 when single mode (pooler excluded + `yamlOnly`); pg-ha 2.5.0 has no descriptor, so its keys are parent fields in the Database step, chosen by the virtual `dbMode` enum (n8n/unleash pattern). `gvc` limited to 1 location.
- **Public access is intentional.** Unlike the templates flipped private this cycle, the credential here is user-created, and a private Keycloak cannot serve browser SSO to anything.
- **HA password rotation must also update the `repl` role (measured on listmonk 1.6.0, 2026-10-14).** postgres-highly-available 2.5.0 uses the same secret password for its replication user `repl`; after `ALTER ROLE <user>` + secret edit + redeploy, the standbys failed with `password authentication failed for user "repl"` while the app kept working on the leader. `ALTER ROLE repl PASSWORD '<new>'` on the leader restored streaming in ~12 s. README and wizard help say so.
- **HA rotation ORDER matters (spike 2026-10-15, postgres-highly-available 2.5.0, 3/3 pass).** `ALTER` + secret edit + force-redeploy of `-postgres-ha` is NOT safe on its own: the platform restarts members highest ordinal first (2→1→0, observed 5/5, undocumented) and the chart's preStop calls `/switchover` with no candidate, so the leader can hand off to a member still on the OLD password. Measured: a diverged timeline that HAProxy routed clients to (spike), and on chatwoot a replica stuck `forked off` for 19 min while the leader streamed ~16 GB/min to it (~$30 egress, single location). Safe order (README section): switch the leader to `-0` first, ALTER user + `repl` on `-0`, edit the secret, redeploy — `-0` restarts last. Recovery: `POST /reinitialize {"force":true}` on the stuck member. Also: Patroni's DCS config keeps the INSTALL-time password readable unauthenticated at `:8008/config` (survives rotation) — README step 7 PATCHes it out; chart fix + preStop candidate hardening tracked on 5284.
