# Listmonk — Maintainer Briefing

## What it is
- Self-hosted newsletter and mailing-list manager (~22k stars): campaigns, subscriber lists, public subscription pages, transactional mail API. Single Go binary over PostgreSQL.
- License: AGPL-3.0 (strong open source: anyone offering a modified version as a service must share their changes) — accepted per catalog precedent (metabase, mimir, gitea).

## Common use cases
- Newsletters/marketing campaigns without per-subscriber SaaS pricing (Mailchimp replacement).
- Companion to the content stack: ghost (publish) + umami (measure) + listmonk (mail).
- Transactional email (password resets, receipts) via its HTTP API.
- Subscriber/list management with public opt-in pages and archives.

## Architecture on cpln
| Resource | Purpose |
|---|---|
| `{release}-listmonk` (stateful, 1 replica, :9000 http) | Listmonk server + campaign workers |
| `{release}-listmonk-uploads` volumeset (10 GiB, `/listmonk/uploads`) | uploaded media (images in emails) |
| user's `admin.secretName` secret (dictionary, **prerequisite**) | bootstrap Super Admin `username`/`password` — user-created since 1.1.0, never by the chart |
| user's DB credentials secret (dictionary, **prerequisite since 1.6.0**) | `username`/`password`/`database`; named by `postgres.config.credentialsSecretName` (default) or `postgresHA.config.credentialsSecretName` (HA). The active subchart initializes from it and listmonk reads all three keys as `LISTMONK_db__*` env vars. Chart-created from `postgres.credentials.*` in 1.2.0–1.5.0 |
| identity + policy | `reveal` on exactly the user's admin secret + the active DB credentials secret |
| `postgres` subchart (default, **3.4.1** since 1.2.0 — creates no secret of its own) or `postgresHA` subchart (opt-in, **2.5.0** since 1.3.0 — creates no credentials secret; `{release}-postgres-config` holds only backup bucket/region, and only when backups are on) | all data except media files; exactly one enabled (XOR validated) |

- Schema init + admin creation are automatic on first boot (`--install --idempotent` + `LISTMONK_ADMIN_*` env) — zero-touch, no manual step. A boot-time DB-wait loop absorbs Postgres warm-up (~35 s of retry lines, no crash-loop).
- Public HTTPS on by default (subscribers must reach subscription/unsubscribe pages); admin UI protected by listmonk's own login.

## Availability posture
- **Single replica, permanently — no `replicas` knob, ever.** Upstream owner (issue #2052): "A listmonk DB can only have one listmonk instance acting on it"; overlapping instances risk duplicate campaign sends. Architectural, not an edition/paywall limit.
- Rollouts are deliberately **no-surge** (`maxSurgeReplicas: 0%` + `scalingPolicy: OrderedReady`) — old instance stops before the new one starts. Measured: a **4 s** non-200 gap on upgrade and the replica sampler never saw 2 replicas; full replica replacement = ~15 s unavailable. Durability = Postgres (HA chart optional) + a seconds-fast Go restart.

## Troubleshooting / considerations
- **No mail sends until SMTP is configured post-install** in **Admin → Settings → SMTP**. By design — listmonk stores SMTP in its database, not in boot config, so it is not a values knob. Users bring their own relay (SES, Mailgun, …); we never bundle mail delivery. A campaign started without SMTP fails gracefully per subscriber (`error sending message … EOF`, campaign `finished` with `sent: 0`) — health stays 200 and the workload stays ready; that is not a crash.
- **Root URL (public links/email) is set automatically at boot (1.5.0).** `app.root_url` is a DB-only setting (not env/config-overridable) that `--install` seeds to `http://localhost:9000`, which breaks every public link (subscribe/unsubscribe/archive/tracking) and email link. The boot script now sets it via a guarded SQL UPDATE after `--install/--upgrade`: `rootUrl` value if set (enforced every boot), else derived from `CPLN_GLOBAL_ENDPOINT` and applied ONLY while the value is still the untouched localhost default (so a UI/custom-domain change is respected). Needs `psql`, which the alpine image lacks, so it's `apk add`-ed at boot; an apk failure is tolerated (WARN, boot continues, root_url stays default). Verified: DB holds the canonical endpoint and public pages emit zero `localhost:9000` links. If links are still wrong, check the boot log for the `apk`/`WARN` line and set `rootUrl` explicitly.
- **Workload wedged with ZERO log lines** → a prerequisite secret (admin, or since 1.6.0 the DB credentials — which also wedges the postgres workload) does not exist. The container never starts, so `cpln logs` is empty; the diagnostic is `status.versions[].message` from `cpln workload get-deployments … -o yaml` (**not** plain `get`). Self-heals in ~5.5–10.5 min once created, or force a redeployment (~90 s).
- **Container exits immediately naming the admin secret** → the `username` is under 3 chars or the `password` under 8. Upstream's `--install` would otherwise fail forever inside the DB-wait loop, printing "waiting for database..." and pointing at the wrong thing; the boot script checks the lengths first because they are no longer visible at render (1.1.0).
- **Admin password edited in the secret but login unchanged** → expected: `LISTMONK_ADMIN_*` is read only during first install; accounts live in the database afterwards. Change passwords in the UI (Admin → Users). Restart is proven idempotent (`skipping install as database appears to be already setup` — no re-seed, no superadmin re-create).
- **Two instances must never run at once** — do not hand-scale the workload or point a copy at the same DB; duplicate/conflicting campaign sends result. The no-surge rollout already prevents overlap during upgrades.
- **Health probes use `/health` (public), not `/api/health`** — the latter requires auth at v6.2.0 (403 unauthenticated) and would fail probes.
- **Boot logs with `waiting for database...`** → Postgres not up yet (normal for ~35 s on first install; the HA path may run two install attempts while HAProxy converges) — only a concern if it persists, which means bad DB credentials.
- **Media storage (S3) is a UI setting, not a template knob** — **Admin → Settings → Media**; the default filesystem store rides the volumeset and survives redeploys. Uninstall deletes the volumeset (media) and the DB volumeset — DB backups do not cover media files.
- **Firewall changes lag the helm upgrade** by ~40–120 s before the mesh enforces them; stateful force-redeployments can also sit queued for a minute or two. Platform behavior, not template.
- **1.2.0 adopted postgres 3.4.1, and listmonk absorbed the break rather than passing it on.** 3.4.0 deleted its `{release}-pg-config` secret and now takes only a secret NAME. Because a parent cannot template a subchart value, the name is a plain value (`postgres.config.credentialsSecretName`) that BOTH sides read: listmonk's `secret-db.yaml` renders it, the subchart's env refs and policy consume it, and `listmonk.db.secretName` points the app at it. Net user-visible change is one rename; **no new prerequisite**, because no human ever types this password. This is the DEFAULT path here, so every default install renders the new secret.
- **The secret name is org-wide, not release-scoped** (forced by the Helm limitation above). Since 1.6.0 the user owns the secret, so two releases pointed at one secret would share credentials but not a database (each has its own postgres); the README tells users to make one per release. (In 1.2.0–1.5.0 the second release on the default name was refused at install.)
- **A stale 1.1.0 values file fails with the SUBCHART's message, not listmonk's.** Helm renders `charts/…` before `templates/…`, so a parent-side guard would be dead code and was deliberately not added. 3.4.1's message appends a clause telling bundled users not to create a secret themselves; the README's "Upgrading from 1.1.0" table carries the rename.
- **1.3.0 extended the same absorption to HA** (pg-ha 2.5.0): `postgresHA.postgres.*` was removed, `listmonk.db.secretName`'s HA branch now names the chart-created secret via `postgresHA.config.credentialsSecretName`, and HA MinIO backup keys became a prerequisite secret. HA upgraders from 1.2.x must carry their existing `postgresHA.postgres.*` values into `postgres.credentials.*` unchanged; pg-ha's removal error tells them to create the secret themselves, which they must ignore (the README's "Upgrading from 1.2.x" says so).
- **1.6.0: the DB credentials became a prerequisite secret** (maintainer ruling 2026-10-14, GitLab 5284 — a parent whose DB subchart takes only a secret NAME must require the user to create it; this narrowed the "bundled plumbing" exception that 1.2.0–1.5.0 relied on). `secret-db.yaml` is gone; `LISTMONK_db__database` now also comes from the secret (it was a plain value), so nothing DB-related is rendered from values. No config file was involved: listmonk is env-only (`--config ''`), and the boot script's `psql` root-URL update already read the `LISTMONK_db__*` env vars, so it needed no change.
- **Upgrading 1.5.0 → 1.6.0 DELETES the chart-created secret** (it leaves the release). The user must create a NEW-name secret holding the CURRENT values (`cpln secret reveal my-listmonk-db-credentials -o yaml` before upgrading), point the active mode's `credentialsSecretName` at it, and drop `postgres.credentials`. Reusing the old name races the deletion. The wizard enforces a new name with a rule keyed on `context.fromVersion < 1.6.0`. Per the batch-1 measurements (unleash/gitea/n8n), the upgrade restarts the bundled postgres too, and a new workload version can sit ~10 min on `is not allowed to reveal the secret` while the new grant propagates; the old version keeps serving. **Not yet measured on listmonk itself.**
- **An empty secret name fails with the SUBCHART's message**, not listmonk's (`charts/…` renders first); listmonk's own `validateDatabaseSecret` empty-name branch is effectively a backstop. The `postgres.credentials` removal check DOES fire with listmonk's message.
- **Password rotation:** `ALTER ROLE` first, `cpln secret edit`, force-redeploy postgres (`{release}-postgres` / `{release}-postgres-ha`), wait ready, then force-redeploy listmonk. A secret edit alone redeploys nothing.
- **Never pin the `nightly` image tag**; upstream is prepping v7.0.0 — expect a config-surface re-check at that bump.
- **HA password rotation must also update the `repl` role (measured on listmonk 1.6.0, 2026-10-14).** postgres-highly-available 2.5.0 uses the same secret password for its replication user `repl`; after `ALTER ROLE <user>` + secret edit + redeploy, the standbys failed with `password authentication failed for user "repl"` while the app kept working on the leader. `ALTER ROLE repl PASSWORD '<new>'` on the leader restored streaming in ~12 s. README and wizard help say so.
- **HA rotation ORDER matters (spike 2026-10-15, postgres-highly-available 2.5.0, 3/3 pass).** `ALTER` + secret edit + force-redeploy of `-postgres-ha` is NOT safe on its own: the platform restarts members highest ordinal first (2→1→0, observed 5/5, undocumented) and the chart's preStop calls `/switchover` with no candidate, so the leader can hand off to a member still on the OLD password. Measured: a diverged timeline that HAProxy routed clients to (spike), and on chatwoot a replica stuck `forked off` for 19 min while the leader streamed ~16 GB/min to it (~$30 egress, single location). Safe order (README section): switch the leader to `-0` first, ALTER user + `repl` on `-0`, edit the secret, redeploy — `-0` restarts last. Recovery: `POST /reinitialize {"force":true}` on the stuck member. Also: Patroni's DCS config keeps the INSTALL-time password readable unauthenticated at `:8008/config` (survives rotation) — README step 7 PATCHes it out; chart fix + preStop candidate hardening tracked on 5284.

## 1.6.1 — HA database image override (CVE-2026-103484, work item 5376)
- **`postgresHA.image: controlplanecorporation/patroni-postgres:0.8`** (new key). The vendored `postgres-highly-available` 2.5.0 defaults to `0.7`, which carries pgvector 0.8.0 (CVE-2026-103484: a role that can build an IVFFlat index can run code on the server); `0.8` carries PGDG pgvector 0.8.7 and is otherwise the same image. Maintainer decision 2026-10-27: override the image in the parent and keep the vendored subchart version; moving to `postgres-highly-available` 2.8.1 is a later batch.
- **`listmonk.validatePostgresHAImage`** (HA mode only) refuses `controlplanecorporation/patroni-postgres` tags `0.1`-`0.7` (with or without `docker.io/`) using `pg-ha.validateImage`'s matching, and also an emptied `postgresHA.image`, because the subchart would then fall back to its `0.7` default. Mirrored by the wizard rule on the new `postgresHA.image` field (Database step, HA group).
- **Single-instance mode is unaffected**: it runs the official `postgres:18`, which ships no pgvector. listmonk does not create the `vector` extension (grep of the chart, plus upstream source), so the README tells only users who created it themselves to run `ALTER EXTENSION vector UPDATE;`.
- **The upgrade restarts the Patroni members, not the proxy: a brief write interruption while the leader changes.** Nothing limits the rollout of a stateful workload (`maxUnavailableReplicas` is dropped there), so the members do not restart one at a time; the HAProxy proxy workload does not restart (helm may print `Updated` for it from a tag bump, but its replicas keep running). The app restart is the longer interruption: the single listmonk replica stops before the new one serves (measured ~83 s); pooled database connections also fail a few writes right after the leader change. Not deployed in this change; the E2E suite onboarded in 1.6.1 (`listmonk/tests/`, HA baseline, `upgradeFrom: 1.6.0`) proves the upgrade and the `pgvector-0-8-7-available` check in CI.
