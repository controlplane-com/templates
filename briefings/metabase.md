# Metabase — Maintainer Briefing

## What it is

- Self-hosted BI/analytics (dashboards, SQL editor, scheduled reports) over the user's own databases. **Free open-source edition only**, licensed AGPL (a strong open-source license: anyone offering a modified version as a service must publish their changes) — the `metabase/metabase` image; paid Pro/Enterprise features and their separate image are excluded entirely.

## Common use cases

- Team dashboards and ad-hoc SQL over Postgres/MySQL/BigQuery/etc. the user already runs
- Scheduled report/dashboard subscriptions by email
- Lightweight internal analytics UI in the same GVC as the data (internal-only mode)
- Pointing at the bundled subchart Postgres as a first data source for evaluation

## Architecture on cpln

| Resource | Purpose |
|---|---|
| workload `{release}-metabase` | Standard (stateless), 1 replica, port 3000 http, JVM |
| user's `admin.secretName` secret (dictionary, **prerequisite**) | Admin bootstrap `email` + plaintext password (the setup API needs plaintext) — user-created since 1.1.0, never by the chart |
| secret `{release}-metabase-start` (opaque) | Start script: MB_SITE_URL derivation + localhost admin bootstrap |
| identity + policy | `reveal` on exactly: the start script and the user's admin, encryption-key and DB credentials secrets, by name |
| DB credentials secret (dictionary, **user-created** since 1.5.0) | `username`/`password`/`database` — named by `postgresHA.config.credentialsSecretName` (HA) or `postgres.config.credentialsSecretName` (single); the active subchart initializes from it and Metabase's `MB_DB_USER`/`MB_DB_PASS`/`MB_DB_DBNAME` read it as discrete env vars (no URL). 1.2.0–1.4.0 rendered it from `postgres.credentials.*` (`templates/secret-db.yaml`, deleted in 1.5.0) |
| subchart `postgresHA` (default, **2.5.0** since 1.3.0) / `postgres` (dev, **3.4.1** since 1.2.0) — neither creates a credentials secret of its own | App DB — n8n dual-mode mechanics verbatim (exactly-one validation, HAProxy leader endpoint). pg-ha's `{release}-postgres-config` now holds only backup bucket/region, and only when HA backups are on |

- **No volumeset** — all state in Postgres; H2 never used.
- First-boot admin created in-container via `POST /api/setup` (auto-generated token, cleared on use); **readiness probe requires `has-user-setup:true`** → no externally reachable setup window, fail-closed.

## Key knobs

`image` | `resources` (2Gi/1CPU default; JVM) | `encryptionKey.secretName` (prerequisite opaque secret, ≥16 chars) | `admin.secretName` (prerequisite dictionary secret: `email` + `password`) + `admin.firstName`/`admin.lastName` (plain values) | `siteName` | `publicAccess.enabled` (default true) | `internalAccess.type` | `postgresHA.config.credentialsSecretName` / `postgres.config.credentialsSecretName` (both default `my-metabase-db-credentials`; REQUIRED prerequisite dictionary secret for the mode in use, **1.5.0+**; must exist BEFORE install; org-wide, so one per release) | `postgresHA.*` / `postgres.*` (replicas, capacity, backups — pass-through) | `*.backup.minio.credentialsSecretName` (default `my-metabase-minio-credentials`, prerequisite only for MinIO backups; HA since 1.3.1, single since 1.2.0)

## Troubleshooting / considerations

- **Workload wedged with ZERO log lines** → a prerequisite secret (admin, encryption key, or DB credentials) does not exist. The container never starts, so `cpln logs` is empty; the diagnostic is `status.versions[].message` from `cpln workload get-deployments … -o yaml` (**not** plain `get`). Self-heals in ~6–12 min once created (measured 2026-10-14 for a missing DB secret: postgres 9m50s, Metabase 11m25s), or force a redeployment of the database then Metabase.
- **Workload never ready + `cpln-bootstrap: ERROR` in logs** → admin bootstrap failed; most common: the password in the admin secret is too weak for Metabase's server-side complexity check (needs letters **and** digits, 8+), it contains a `"` or `\` (the start script rejects those before POSTing — they would break the setup JSON body), or the `POST /api/setup` body shape changed upstream. Unready = intentionally unexposed (fail-closed), not a probe bug.
- **Encryption key is crown jewels**: user-created opaque secret; losing/changing it forces re-entering every saved database connection. Never rotate casually (offline `rotate-encryption-key` command exists upstream).
- **Admin password changes post-install happen in the Metabase UI**, not in the secret — the admin secret only matters at first boot; editing it does NOT change an existing admin (has-user-setup is permanent, bootstrap skips). 1.1.0 moved `admin.email`/`admin.password` out of values into that prerequisite secret (2026-08-07 ruling: a credential guarding a public human-facing login); `fail` guards name the replacement, no shims.
- **Reinstall against retained subchart data** = setup already done: bootstrap skips, old credentials apply. Full reset requires uninstall (deletes subchart volumesets) + reinstall.
- **First boot / upgrades run app-DB migrations** — liveness initialDelay is deliberately long (240s); don't "fix" slow first boot by tightening probes.
- **JVM memory**: heap is set to 75% of container memory via hardcoded `JAVA_OPTS`; OOM under load → raise `resources.memory`, upstream sizing is +2GB per 20 concurrent users.
- **Do not set `MB_SETUP_TOKEN`** (upstream bug leaves the frontend stuck on /setup); the design reads the auto-generated token instead.
- **Never disable `postgresHA.proxy.enabled`** — HAProxy is Metabase's stable DB endpoint (validation blocks it).
- **1.5.0: the DB credentials became a prerequisite secret (maintainer ruling 2026-10-14, work item 5284).** Rule: when a dependency requires a pre-existing credential secret, the parent requires it too, rather than rebuilding it from plaintext values. 1.2.0–1.4.0 kept `postgres.credentials.*` as values under the bundled-plumbing exception and rendered `secret-db.yaml` in both modes, which put the DB password in the Helm release. `postgres.credentials` now fails at render (`metabase.validateDatabaseSecret`, mirrored in the wizard). `MB_DB_DBNAME` now reads the secret in both modes (1.4.0 used the plain value on the single path). Metabase takes user/password/database as discrete env vars, so no URL assembly and no character restriction.
- **Upgrading 1.4.0 → 1.5.0 deletes the chart-created DB secret**, because the new chart no longer renders it. The user must create a secret under a NEW name holding the CURRENT credentials (the data dir keeps the password it was initialized with) and point the active mode's `credentialsSecretName` at it. The wizard enforces the new name with a rule keyed on `context.fromVersion < 1.5.0`. Expect the bundled postgres to restart and the new workload versions to stall ~10 min on `is not allowed to reveal the secret` (authorization edge cache, measured on gitea 1.3.0 / siblings) before clearing on their own. **Not yet live-tested on metabase.**
- **Password rotation** = `ALTER ROLE` → `cpln secret edit` → force-redeploy the postgres workload (`{release}-postgres-ha` / `{release}-postgres`), wait ready → force-redeploy `{release}-metabase`. A `cpln://` reference is resolved only at replica start.
- **Both name knobs exist because a parent cannot template a subchart value**: each subchart reads its own `config.credentialsSecretName`; `metabase.postgres.secret.name` picks the active one. The secret name is org-wide — two releases need two secrets.
- **Older upgraders get the subchart's own removal errors** (`postgres.config.username` from postgres 3.4.x, the `postgres` block from pg-ha 2.5.0); their advice — create a dictionary secret — is now correct for metabase too (1.2.0–1.4.0 READMEs told users to ignore it).
- **Wizard (1.5.0, first descriptor):** imports postgres 3.4.1 (single mode; pooler excluded + yamlOnly); pg-ha 2.5.0 has no descriptor, so its keys are parent fields in the Database step, picked by a virtual `dbMode` chooser like unleash/n8n. `gvc` limited to 1 location (both DBs are single-location).
- Uninstall deletes the app DB (dashboards/questions/users); the prerequisite encryption-key secret survives (user-owned). Enable subchart backups if data matters.
- **HA password rotation must also update the `repl` role (measured on listmonk 1.6.0, 2026-10-14).** postgres-highly-available 2.5.0 uses the same secret password for its replication user `repl`; after `ALTER ROLE <user>` + secret edit + redeploy, the standbys failed with `password authentication failed for user "repl"` while the app kept working on the leader. `ALTER ROLE repl PASSWORD '<new>'` on the leader restored streaming in ~12 s. README and wizard help say so.
- **HA rotation ORDER matters (spike 2026-10-15, postgres-highly-available 2.5.0, 3/3 pass).** `ALTER` + secret edit + force-redeploy of `-postgres-ha` is NOT safe on its own: the platform restarts members highest ordinal first (2→1→0, observed 5/5, undocumented) and the chart's preStop calls `/switchover` with no candidate, so the leader can hand off to a member still on the OLD password. Measured: a diverged timeline that HAProxy routed clients to (spike), and on chatwoot a replica stuck `forked off` for 19 min while the leader streamed ~16 GB/min to it (~$30 egress, single location). Safe order (README section): switch the leader to `-0` first, ALTER user + `repl` on `-0`, edit the secret, redeploy — `-0` restarts last. Recovery: `POST /reinitialize {"force":true}` on the stuck member. Also: Patroni's DCS config keeps the INSTALL-time password readable unauthenticated at `:8008/config` (survives rotation) — README step 7 PATCHes it out; chart fix + preStop candidate hardening tracked on 5284.
- **1.5.1: HA database image override for CVE-2026-103484 (work item 5376, 2026-10-27).** The vendored postgres-highly-available 2.5.0 defaults to `controlplanecorporation/patroni-postgres:0.7` (pgvector 0.8.0). 1.5.1 sets `postgresHA.image: controlplanecorporation/patroni-postgres:0.8` (pgvector 0.8.7) instead of moving to pg-ha 2.8.1, which was unpublished at the time; move to the subchart version that carries the fix in a later version and drop the override then. `metabase.validatePostgresHAImage` (HA mode only) refuses patroni-postgres tags 0.1-0.7 and an empty value (which would fall back to the subchart's 0.7), mirrored by a wizard rule on `postgresHA.image`. The upgrade restarts the Patroni members (unconstrained stateful rollout), giving a brief write interruption while the leader changes; the HAProxy proxy workload does not restart (stays `Unchanged`; measured on the chatwoot and keycloak rounds). The app workload restarts as on any version upgrade; Metabase runs one replica, so that is the longer interruption. `ALTER EXTENSION vector UPDATE;` only refreshes the catalog version. E2E tests onboarded in this version (`metabase/tests/`). Not live-tested at build time.
