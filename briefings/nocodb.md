# NocoDB — Maintainer Briefing

## What it is
- No-code database / spreadsheet-style app builder — the self-hosted Airtable alternative: grid, kanban, gallery and calendar views, forms, automations and a REST/GraphQL API over your own data.
- License: **NocoDB Sustainable Use License** ("fair-code", source-available and free to self-host — nothing to buy, register or activate). Selling NocoDB as a hosted service to others needs a commercial license. Passes the catalog's cost-to-the-user test.

## Common use cases
- A shared team database non-developers can build and edit — trackers, CRMs, inventories, content calendars — with no SQL.
- A friendly UI and REST API on top of a Postgres database the team already owns.
- The data layer behind automations built in the catalog's `n8n` or `tooljet` templates.
- Public forms and shared views for collecting data from outside the org.

## Architecture on cpln
| Resource | Purpose |
|---|---|
| `{release}-nocodb` (stateful, :8080) | UI + REST/GraphQL API + live updates in one image; replica count from `nocodb.replicas`; runs meta-database migrations on boot |
| `{release}-nocodb-redis` + `-redis-vs` volumeset | bundled single-node Redis (AOF, `noeviction`): job/event pub-sub, metadata cache, rate limiter — **required**, all three needed above one replica |
| `postgres` 3.4.1 **or** `postgres-highly-available` 2.5.0 (aliased `postgresHA`) | the metadata store — every base, table, view, user and automation |
| DB credentials secret (dictionary, **user-created prerequisite since 1.4.0**) | `username`/`password`/`database`, read by the active database subchart AND by NocoDB, in **both** modes. Named by `postgres.config.credentialsSecretName` (single) or `postgresHA.config.credentialsSecretName` (HA). 1.1.0-1.3.x rendered it from `postgres.credentials.*` (`templates/secret-db.yaml`, deleted in 1.4.0) |
| `{release}-nocodb-storage` volumeset | local attachments at `/usr/app/data`; **rendered only when `storage.type: local`** |
| Redis credentials secret (dictionary, **user-created prerequisite since 1.4.0**) | key `password`, named by `redis.credentialsSecretName`; read by Redis (`--requirepass $(REDIS_PASSWORD)`) and by NocoDB (`NC_REDIS_URL` assembled from `$(NC_REDIS_PASSWORD)`). 1.0.0-1.3.x rendered it from `redis.auth.password` into the chart-created `{release}-nocodb-creds` (key `redisPassword`), deleted in 1.4.0 |
| identity + policy | `reveal` on exactly the mounted secrets; carries the AWS cloud-account link in keyless S3 mode |

- One stateless app tier over shared Postgres + Redis. No clustering protocol, no quorum, no per-replica addressing — replicas share the database and the cache and nothing else.
- Public HTTPS on the automatic `*.cpln.app` endpoint by default; live updates ride the same port over HTTP long-poll.

Values must be URL-safe (letters/digits/`-`/`_`) — they are spliced unencoded into `NC_DB`; the README says so, nothing enforces it. `postgres.credentials` is render-rejected (`nocodb.validateDatabaseSecret`) |

Prerequisite secrets (create BEFORE install; verbatim-verified):
`cpln secret create-dictionary --name my-nocodb-secrets --entry NC_AUTH_JWT_SECRET="$(openssl rand -hex 64)" --entry NC_CONNECTION_ENCRYPT_KEY="$(openssl rand -hex 32)"`
`cpln secret create-dictionary --name my-nocodb-db-credentials --entry username=nocodb --entry password="$(openssl rand -hex 24)" --entry database=nocodb` (1.4.0)
`cpln secret create-dictionary --name my-nocodb-redis --entry password="$(openssl rand -hex 24)"` (1.4.0)

## Availability posture
- **The app tier scales horizontally in the free edition** — the `replicas` knob shipped because both hard-gate rows passed. U2: a cold 2-replica install is serialized by `scalingPolicy: OrderedReady`, so migrations ran on R0 only (migration log-lines **R0: 41, R1: 0**), reproduced on two independent cold installs. U1: cross-replica delivery proven — a job created on replica-0 was streamed from replica-1, and a held listener on replica-1 returned immediately on a Redis `PUBLISH`.
- **Measured:** rolling upgrade at 2 replicas **434/434 HTTP 200**; abrupt `kill -9` of one replica **6 × HTTP 503 of 289 requests** in an ~11 s window, then clean recovery (an insert during the window succeeded).
- **The bundled Postgres defaults to single-instance**; `postgresHA.enabled: true` + `postgres.enabled: false` is the one-flag HA path (3 Patroni + 3 etcd + HAProxy, ready ≈ 6 min from install).

## Troubleshooting / considerations
- **Live updates are NOT websockets.** At 2026.07.0 socket.io is telemetry-only — verified at the shipped tag (the gateway registers only inbound `page`/`event` beacons), it accepts a socket bearing a bogus token, and an authenticated socket received **zero** frames across five data mutations. The real path is `POST /jobs/listen` HTTP long-poll over Redis pub-sub. Anyone debugging "changes aren't appearing" must look at Redis and that endpoint, never at websocket upgrade.
- **Redis is not optional.** It carries job/event pub-sub, the metadata cache and the rate limiter; all three are required once `replicas > 1`. NocoDB speaks only a plain `redis://` URL (no Sentinel), which is why the bundled single node is used rather than the `redis` template.
- **The first `helm upgrade` after any install briefly bounces the bundled Redis** even when nothing about Redis changed — the rendered Redis workload is byte-identical across that upgrade, yet its version goes 2 → 3; later upgrades report `Unchanged`. NocoDB exits (exit code 1, ioredis `EPIPE` → `Connection terminated unexpectedly`) rather than reconnecting. At `replicas: 1` the public endpoint returned `503 no healthy upstream` for roughly a minute; at `replicas: 2` it was invisible (434/434 200s). Expect "why was it briefly down after a config change?" — this is the answer.
- **A fresh install can show one scary crash in the logs.** Replica-0's first boot may race Postgres/Redis availability and exit; it self-heals on the automatic restart ~20 s later.
- **The prerequisite secret must exist BEFORE install.** A missing `secrets.name` wedges the deployment and looks like a broken install, not a missing prerequisite. First thing to check on any "it never goes ready" report. Both keys are write-once: rotating `NC_AUTH_JWT_SECRET` logs out every user, and changing `NC_CONNECTION_ENCRYPT_KEY` makes stored external-datasource credentials undecryptable (no upstream re-encryption path).
- **`replicas > 1` with local storage is refused at render time** on purpose — per-replica volumes would 404 half the attachment downloads. S3 comes first.
- **U2 rests on a platform behavior, not a lock.** NocoDB takes no migration lock; correctness of a cold multi-replica install depends entirely on the platform continuing to serialize stateful scale-up via `OrderedReady`. If that ever changes, this template races silently.
- **The readiness probe cannot be tightened.** `periodSeconds: 15 × failureThreshold: 20` **is** the 300 s first-boot migration budget, and the platform caps the threshold at 20. The ~11 s ejection window on abrupt replica death sits inside one probe period — a deliberate trade-off, not a bug.
- **The attachment limit is a byte count.** `storage.fileUploadSizeLimit` maps to `NC_ATTACHMENT_FIELD_SIZE`; over-limit uploads are **rejected, not truncated** — HTTP 413 `{"message":"File too large","error":"Payload Too Large"}`. Applies in both storage modes. `0` is render-rejected (it would silently fall back to the 20 MiB upstream default).
- **The image runs as root and no `securityOptions` is set — deliberate.** The nocodb image declares no `USER`, so the process writes to the mounted volumeset directly (confirmed live: `root root` ownership on `/usr/app/data`). Do not add a `filesystemGroupId`.
- **Signup is open by default.** With public access on, anyone reaching the URL can create an account; invite-only is an in-app setting (Team & Settings), not an env var, so it must be turned on in the UI after install.
- **`admin.secretName` re-applies on every boot** — a password changed in the UI silently reverts at the next restart. Leave it empty, or treat the secret as the source of truth. (Not exercised live; the empty default was, and the first signup returned `roles: org-level-creator,super` as documented.)
- **Background jobs run inside the web process.** Community Edition has no separate worker, so a long import, export or base duplication dies with the replica running it and must be re-run. Multi-replica buys request availability and rolling upgrades, not job durability.
- **`internalAccess.type` changes are not instantaneous** — ~30 s from the spec going live to in-GVC traffic actually being rejected. Re-poll before concluding a knob is broken.
- **Uninstall deletes all data** — the database and storage volumesets go with the release (measured on chatwoot 1.3.0, same shape); the old "data survives reinstall" note was false.
- **SSO/SAML/OIDC, audit logs and row-level security are Enterprise-gated** in the same image and need a purchased license key this template never sets. Expect "why is SSO greyed out" — the answer is edition, not configuration.
- **The DB credentials are a user-created prerequisite secret since 1.4.0 (work item 5284).** Rule (maintainer 2026-10-14): when a dependency (`postgres` 3.4.x, `postgres-highly-available` 2.5.x) takes only a credentials-secret NAME, the parent requires the user to create that same secret — no plaintext `postgres.credentials.*` the parent turns into a secret. This narrows CLAUDE.md's bundled-plumbing exception. The Redis password followed in the same 1.4.0 (maintainer 2026-10-16: each datastore gets its OWN dictionary secret). History: 1.1.0 moved single-instance `postgres.config.{username,password,database}` → `postgres.credentials.*` (chart-built secret), 1.2.0 did the same for HA (`postgresHA.postgres.*` removed), 1.4.0 removed `postgres.credentials` and `secret-db.yaml`.
- **The 1.3.x → 1.4.0 upgrade DELETES the old chart-created secret** (it is a release resource that no longer renders). The user must create a secret under a NEW name holding the CURRENT values (`cpln secret reveal <old> -o yaml` before upgrading) and point the mode's `credentialsSecretName` at it. Reusing the old name means Helm deletes the secret the database and NocoDB then reference. The wizard enforces the new name (rule keyed on `context.fromVersion < 1.4.0`). Expected during the upgrade: the bundled PostgreSQL restarts (it now reads the new secret) so NocoDB briefly loses its DB, and the new workload version can sit ~10 min on `is not allowed to reveal the secret` while the new grant propagates (old version keeps serving).
- **`NC_DB` is now assembled entirely at container start.** `pg://<host>:5432/?u=$(NC_PG_USER)&p=$(NC_PG_PASSWORD)&d=$(NC_PG_DATABASE)`, all three env vars `cpln://secret/<db secret>.<key>` declared above `NC_DB`. 1.1.0-1.3.x rendered the database NAME from values into `d=` at render time (the "second read" CLAUDE.md flags) and render-checked the password charset; both went with the plaintext values. The u/p `$(VAR)` expansion inside `NC_DB` shipped since 1.1.0; the `d=$(NC_PG_DATABASE)` piece is new in 1.4.0 and was **[UNPROVEN] at build** — confirm in the live test that the meta DB is the secret's `database`. Values are not URL-encoded, so a non-URL-safe value breaks the connection silently-ish (NocoDB crash-loops on connect).
- **Redis password (1.4.0): no plaintext left in values.** Rotation = `cpln secret edit` → force-redeploy `-nocodb-redis` AND `-nocodb` (Redis keeps no password on disk; both read it only at start; short interruption). The 1.3.x → 1.4.0 upgrade deletes `{release}-nocodb-creds`, so the new secret needs a different name holding the current password (`cpln secret reveal {release}-nocodb-creds -o yaml` → `redisPassword`); the wizard refuses `{release}-nocodb-creds` on that upgrade. **[UNPROVEN]** live: the upgrade path with a carried password, and the rotation order.
- **Rotating the DB password:** single-instance = `ALTER ROLE` → `cpln secret edit` → force-redeploy `-postgres`, wait ready → force-redeploy `-nocodb`. HA = the leader-to-`-0` switchover procedure in the README (also rotates the `repl` role); a plain redeploy can promote a member still holding the old password and split the cluster.
- **Secret names are org-wide and cannot be templated.** Helm resolves subchart values before rendering and postgres does not `tpl` the name, so it cannot contain `.Release.Name`. Since 1.4.0 the secret is user-owned, so two releases pointed at one secret both work (each database initializes with the same credentials) — the old "refused at install" collision no longer applies.
- **An upgrader carrying the 1.0.x keys gets postgres's own error**, not a nocodb one: Helm renders `charts/` before `templates/`, so the subchart's `config.username was REMOVED in postgres 3.4.0` always wins. Since 1.4.0 its advice to create the secret is correct. A parent-side guard would be dead code — do not add one. (`postgres.credentials`, by contrast, is unknown to the subchart, so the parent's `validateDatabaseSecret` does fire.)
- **MinIO backup keys are a prerequisite dictionary secret on both paths** (`accessKey`/`secretKey`) — `postgres.backup.minio.credentialsSecretName` since 1.1.0 (postgres 3.4.0), `postgresHA.backup.minio.credentialsSecretName` since 1.2.1 (pg-ha 2.5.0). Inline keys fail the render.
- **Not exercised in testing** (call out if a report touches them): all `smtp.*` rows, S3-compatible storage via `endpoint` + `forcePathStyle` + static keys, an explicit `nocodb.siteUrl`, `postgresHA` leader-kill failover, `internalAccess.type` `same-org`/`workload-list`, and the backup blocks (render-only, covered by the dependency templates).
- **In-GVC webhooks need `allowLocalWebhooks: true` (1.3.0).** NocoDB's SSRF guard refuses any webhook to a private IP by default, so a hook aimed at another workload (`*.cpln.local`) silently fails until the flag is set. Verified with the flag on: an after-insert hook to an in-GVC HTTP sink delivered (POST arrived from NocoDB's axios client). The v3 hooks API is fiddly — `operation` must be an ARRAY and `version: "v3"` is required (older shapes are rejected with "hook version is deprecated").
- **MCP is per-base and UI-created (1.3.0 docs).** Base → **Settings → MCP Server → + New MCP Endpoint** yields an endpoint URL + `xc-mcp-token`. It IS available on the Community edition (the MCP Server tab is NOT "Business"-gated, unlike Data Permissions / Syncs / Variables / Snapshots). Register with `claude mcp add --transport http nocodb <url> --header "xc-mcp-token: <tok>"` — the **direct HTTP transport works** end to end (validated: connects, `tools/list` returns 11 tools, `queryRecords` returns real rows). The `mcp-remote` npx bridge NocoDB's UI suggests is NOT required for Claude Code. Account-level MCP/OAuth is Enterprise-gated and absent here.
- **First-boot Postgres race is self-correcting, not a boot-gate.** If NocoDB beats Postgres on a fresh volumeset it crashes once (exit 1, "EXCEPTION ... in PGClient @ createDatabaseIfNotExists / Connection terminated unexpectedly"), then restarts and migrates cleanly. One restart on a brand-new install is expected and healthy — it is the correct crash-and-retry, NOT the empty-schema false-ready trap. A dbGate (as twenty/tooljet added) would make the boot cleaner and is a reasonable follow-up, but it is not a defect.

## 1.4.1 — HA database image override (CVE-2026-103484, work item 5376)
- **`postgresHA.image: controlplanecorporation/patroni-postgres:0.8`** (new key). The vendored `postgres-highly-available` 2.5.0 defaults to `0.7`, which carries pgvector 0.8.0 (CVE-2026-103484: a role that can build an IVFFlat index can run code on the server); `0.8` carries PGDG pgvector 0.8.7 and is otherwise the same image. Maintainer decision 2026-10-27: override the image in the parent and keep the vendored subchart version; moving to `postgres-highly-available` 2.8.1 is a later batch.
- **`nocodb.validatePostgresHAImage`** (HA mode only) refuses `controlplanecorporation/patroni-postgres` tags `0.1`-`0.7` (with or without `docker.io/`) using `pg-ha.validateImage`'s matching, and also an emptied `postgresHA.image`, because the subchart would then fall back to its `0.7` default. Mirrored by the wizard rule on the new `postgresHA.image` field (Database step, HA group).
- **Single-instance mode is unaffected**: it runs the official `postgres:18`, which ships no pgvector. NocoDB does not create the `vector` extension (grep of the chart, plus upstream source), so the README tells only users who created it themselves to run `ALTER EXTENSION vector UPDATE;`.
- **The upgrade restarts the Patroni members, not the proxy: a brief write interruption while the leader changes.** Nothing limits the rollout of a stateful workload (`maxUnavailableReplicas` is dropped there), so the members do not restart one at a time; the HAProxy proxy workload does not restart (stays `Unchanged`; measured on the chatwoot and keycloak rounds). The app workload restarts as on any version upgrade; with a single app replica that is the longer interruption. Not deployed in this change; the E2E suite onboarded in 1.4.1 (`nocodb/tests/`, HA baseline, `upgradeFrom: 1.4.0`) proves the upgrade and the `pgvector-0-8-7-available` check in CI.
