# RabbitMQ — Maintainer Briefing

## What it is
- RabbitMQ, the MPL-2.0 message broker: queues, routes and delivers messages between services over AMQP 0-9-1, with the management plugin and the Prometheus plugin both on.
- Template ships a **single node, single replica** stateful workload on the official `rabbitmq:3-management` image, with one persistent volume at `/var/lib/rabbitmq`. No clustering, no HA — a reschedule or an upgrade is a short outage for every connected client.
- Internal to the GVC only. There is deliberately no `publicAccess` knob.

## Common use cases
- Work queues and background jobs between services in the same GVC (Celery, Sidekiq, Bull, MassTransit).
- Pub/sub fan-out and topic routing where the app wants AMQP exchanges rather than a log (Kafka's shape) or a list (Redis's shape).
- Buffering bursty producers ahead of a slower consumer, with the volume set absorbing the backlog.

## Architecture on cpln
| Resource | Purpose |
|---|---|
| workload `{release}-rabbitmq` (stateful, 1 replica) | Broker: AMQP `5672`, management UI `15672`, metrics `15692` |
| volumeset `{release}-rabbitmq-vs` (10 GiB, ext4) | Mnesia store: messages, queues, **the user database, and the Erlang cookie** |
| secret `{release}-rabbitmq-config` (opaque, plain) | `rabbitmq.conf` — now carries only `listeners.tcp.default` |
| identity + policy | `reveal` on exactly two secrets: the chart's config secret and the user's credentials secret |

- **No AWS/GCP identity bindings at all** — this template never had `aws::ReadOnlyAccess`, so the tier-2 sweep had nothing to remove here.
- **No Erlang cookie value.** The cookie is generated by the broker on first boot into `/var/lib/rabbitmq/.erlang.cookie` (the image sets `HOME=/var/lib/rabbitmq`) and lives on the volume set. It is never a knob, never in the Helm release. If clustering is ever added, the cookie becomes a prerequisite secret — same class as mongodb-cluster's replica-set keyfile.

## Key knobs (shipped 1.2.0 defaults)
`credentialsSecretName` (`my-rabbitmq-credentials`, **must exist before install**) | `image.repository` (`rabbitmq:3-management`) | `cpu`/`memory` (200m / 250Mi) | `timeoutSeconds` (30) | `internalAccess.type` (`same-gvc`) | `rabbitmq_conf.listeners_tcp_default` (5672) | `env.RABBITMQ_CONFIG_FILE` (`/etc/rabbitmq/rabbitmq.conf`) | `volumeset.volume.initialCapacity` (10) / `.fileSystemType` (ext4) / `.performanceClass` (general-purpose-ssd)

## Troubleshooting / considerations
- **Security history — 1.1.1 and earlier ship a working credential.** `rabbitmq_conf.default_user: user` / `default_pass: changeMe`, published in our public repo, used as-is by every install that did not override it. Not just the management-UI login: these are the **AMQP credentials in every producer's and consumer's connection string**. Anyone on ≤1.1.1 should treat the broker as compromised and rotate, not merely upgrade. Note the key is `default_pass`, not `password` — a keyword scan for `password:` misses it, which is nearly what happened.
- **THE CREDENTIAL CANNOT GO THROUGH `rabbitmq.conf`.** A `cpln://secret/...` reference is interpolated only in an **env var**; inside a mounted config-file secret it lands as that literal string and the broker boots with a username of `cpln://secret/…`. So 1.2.0 passes `RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS` as env vars, which **RabbitMQ 3.9+ reads natively** — the docker-library entrypoint stopped handling them in 3.9 and now only errors on the `_FILE` variants (verified against the upstream entrypoint and the official image docs). Do not "tidy" these back into the config file.
- **The default user is written on FIRST BOOT ONLY.** The volume set holds the user database, so changing the secret and redeploying does not change the broker's credentials. Rotate with `rabbitmqctl change_password`, or uninstall (destroying the volume set and every message) and reinstall. This is the most likely "I changed the password and it still accepts the old one" report.
- **A missing prerequisite secret wedges silently.** `cpln logs` returns **zero lines** — the container never starts. The only diagnostic is `cpln workload get-deployments {name} --gvc {gvc} -o yaml` → `status.versions[].message` (`get-deployments`, NOT plain `get`). Self-heals in ~6–8 min once the secret exists, or ~90 s with a forced redeployment.
- **`firewall` was replaced by `internalAccess` in 1.2.0.** The old block's `external_*` keys were *commented out* in values, so the workload rendered **no external firewall block at all** and inherited whatever the API defaults to. 1.2.0 declares the external block explicitly with inbound closed and outbound `0.0.0.0/0`, and `fail`-guards the old `firewall` key.
- **Two knobs were dead and are now fixed.** `diskCapacity: 10` was referenced by no template — a user setting it to 100 got 10 GiB and no warning; it is removed and `fail`-guarded, pointing at `volumeset.volume.initialCapacity`. `timeoutSeconds: 30` was likewise unreferenced while the workload hardcoded `5`; it is now wired to `defaultOptions.timeoutSeconds`, so a 1.2.0 install genuinely gets 30.
- **Drift pre-emption.** Stateful tier, so `rolloutOptions.maxUnavailableReplicas` is **dropped by the API** — 1.1.1 sent `'1'` and got a rolling-restart limit that was never in force; 1.2.0 does not send it. Also now declared: `terminationGracePeriodSeconds: 90`, the secret volume's `recoveryPolicy: retain`, the backfilled `firewallConfig.external` lists, and volumeset `snapshots` (`createFinalSnapshot: true`, `retentionDuration: 7d`).
- **Resource block is limit-only, so bare `cpu`/`memory` is correct** per the 2026-08-05 naming ruling — do not "fix" these to `maxCpu`/`maxMemory`. No `minCpu` is set, so the 4:1 stateful ratio cap does not apply.
- **`image.repository` carries the tag** (`rabbitmq:3-management`) — a floating major tag, so an install today gets the latest 3.13.x and a reinstall next year may get a different patch. `appVersion` is `3-management` to match. Pinning is a candidate follow-up; it was left alone here because a pin is an untested image change.
- **Private by default is reachable.** `cpln port-forward {workload} 15672:15672 --gvc {gvc}` opens the management UI in a browser; the README gives the command. RabbitMQ's management plugin binds `0.0.0.0`, so the Next.js-style loopback trap does not apply — but that specific point is inferred from the plugin's default `management.tcp.ip`, not measured.

## Status — NOT deploy-tested
Build-verified only: bare `helm template` renders clean, all six `fail` guards fire with the right message, the repo linter passes, every README URL resolves 200, and the `cpln secret create-dictionary` / `cpln secret reveal -o yaml` commands were executed for real. **The rendered config secret contains no `cpln://` string** — checked explicitly, since that was the failure mode this change could most easily have shipped.

What only a live deploy can settle: that RabbitMQ actually picks up `RABBITMQ_DEFAULT_USER`/`RABBITMQ_DEFAULT_PASS` when `RABBITMQ_CONFIG_FILE` points at the mounted secret; that an AMQP client authenticates with the secret's credentials; that `defaultOptions.timeoutSeconds: 30` does not disturb long-lived AMQP connections; and the no-op `helm upgrade` drift gate.
