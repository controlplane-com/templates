# Twenty — Maintainer Briefing

## What it is
- Open-source CRM (Salesforce/HubSpot alternative): custom objects, pipelines, views and workflows; one image serves the React UI and the NestJS REST + GraphQL API, plus a background worker.
- License: AGPL-3.0 (strong open source: anyone offering a modified version as a service must publish their changes) — fine per catalog precedent (metabase, mimir, docmost); we ship the unmodified upstream image. Free to self-host, no user cap, no key, no paid gate.

## Common use cases
- "We want to own our customer data" — self-hosted CRM instead of Salesforce/HubSpot.
- Sales pipeline + contact/company records for a small-to-mid team on the customer's own infrastructure.
- API-first CRM back end (REST + GraphQL on the same origin) for internal tooling and workflow automation.
- Pairs with listmonk (outbound email) and chatwoot (support conversations).

## Architecture on cpln
| Resource | Purpose |
|---|---|
| `{release}-twenty` (stateful, :3000) | UI + REST + GraphQL; `twenty.replicas` knob; `filesystemGroupId: 1000` |
| `{release}-twenty-worker` (standard) | BullMQ jobs + cron via `yarn worker:prod`; **fixed at 1 replica, no knob** |
| `{release}-twenty-redis` (stateful, :6379) | bundled single node, AOF + `noeviction` — job queues and cache |
| `{release}-twenty-storage` volumeset | **`fileSystemType: shared` (read-write-many)** — mounted by the server AND worker at `/app/packages/twenty-server/.local-storage`; rendered only in `storage.type: local` |
| `{release}-twenty-redis-vs` volumeset | Redis AOF at `/data` (ext4) |
| `-worker-start` (opaque) | the worker's start script (SERVER_URL derivation, then `exec /app/entrypoint.sh yarn worker:prod`) |
| DB credentials secret (dictionary, **user-created** since 1.4.0) | `username`/`password`/`database` — named by `postgres.config.credentialsSecretName` (single) or `postgresHA.config.credentialsSecretName` (HA); the active subchart initializes from it and Twenty's `PG_USER`/`PG_PASSWORD`/`PG_DATABASE` env vars read it, assembled into `PG_DATABASE_URL` by `$(VAR)` expansion at container start. 1.1.0–1.3.0 built it from `postgres.credentials.*` (`templates/secret-db.yaml`, now deleted). In HA mode `{release}-postgres-config` holds only backup bucket/region, and only when backups are on |
| identity + policy | one identity shared by all three workloads; `reveal` on exactly the mounted secrets plus the user's two prerequisite secrets by name; carries the AWS cloud-account link in keyless S3 mode |
| `postgres` **3.4.1** (default, since 1.1.0) **or** `postgres-highly-available` 2.5.0 aliased `postgresHA` (opt-in) | application database — reused, never reimplemented |

- All HTTP: no `loadBalancer.direct` ports anywhere; public access uses the automatic `*.cpln.app` endpoint.

## Key knobs
| Knob | Default | Note |
|---|---|---|
| `twenty.image` | `twentycrm/twenty:v2.26.1` | Docker tag keeps the `v`; `appVersion` is `2.26.1` |
| `twenty.replicas` | `1` | `>1` REQUIRES `storage.type: s3` (render-validated) and moves boot migrations to the worker |
| `twenty.serverUrl` | `""` | empty = derived from the canonical endpoint; set WITH `https://` for a custom domain |
| `twenty.dbPoolMaxConnections` | `10` | per process; raise with `replicas` carefully (measured 17 live connections at `10`, 14 at `4`) |
| `twenty.resources.*` / `worker.resources.*` | 250m/1000m · 512Mi/2Gi | cpu:minCpu exactly 4.00 — the platform cap; do not widen |
| `secrets.name` | `my-twenty-app-secret` | REQUIRED prerequisite opaque secret; used as **both** `APP_SECRET` and `ENCRYPTION_KEY` |
| `secrets.fallbackName` | `""` | previous key, only during a rotation (`FALLBACK_ENCRYPTION_KEY`) |
| `storage.type` | `local` | `local` \| `s3`; `storage.local.volumeset.capacity: 10` GiB |
| `storage.s3.{bucket,region,endpoint,cloudAccountName,policyName}` | `my-twenty-bucket` / `us-east-1` / `""` / `my-s3-cloud-account` / `my-twenty-s3-policy` | AWS = keyless via cloud account + bucket-scoped IAM policy |
| `storage.s3.auth.secretName` | `""` | static-key dictionary secret — **S3-compatible endpoints only** (render-rejected without `endpoint`) |
| `publicAccess.enabled` / `internalAccess.type` | `true` / `same-gvc` | `workload-list` verified allow AND deny; public off → external 403 |
| `redis.{image,credentialsSecretName,volumeset.capacity}` | `redis:8.10.0` / `my-twenty-redis` / `10` | **REQUIRED prerequisite** dictionary secret, key `password` (1.4.0); embedded unencoded in `REDIS_URL` — letters/digits/`-`/`_` only, nothing enforces it any more. `redis.auth` is render-rejected (`twenty.validateRedisSecret`) |
| `postgres.enabled` / `postgresHA.enabled` | `true` / `false` | **single instance is the default** (`postgres:18`, live 18.4); HA is opt-in (Patroni, PG 17.5). Exactly one must be on |
| `postgres.backup.*` / `postgresHA.backup.*` | `enabled: false` | `aws` \| `gcp` \| `minio`; dependency-covered (render-verified, not re-tested live) |
| `postgres.config.credentialsSecretName` / `postgresHA.config.credentialsSecretName` | `my-twenty-db-credentials` (both) | REQUIRED prerequisite dictionary secret (`username`/`password`/`database`) for the mode in use, **1.4.0+**; must exist BEFORE install; values must be URL-safe (README prose — no render check can see them). `postgres.credentials` fails the render |
| `postgres.backup.minio.credentialsSecretName` / `postgresHA.backup.minio.credentialsSecretName` | `my-twenty-minio-credentials` (both) | genuine prerequisite (`accessKey`/`secretKey`), backup with `provider: minio` only — single since 1.1.0, HA since pg-ha 2.5.0 (values fixed in 1.2.1) |

Prerequisite secrets (create BEFORE install; the shipped README's exact forms, the DB one executed 2026-10-15):
`printf '%s' "$(openssl rand -base64 32)" | cpln secret create-opaque --name my-twenty-app-secret --encoding plain --file -`
`cpln secret create-dictionary --name my-twenty-db-credentials --entry username=twenty --entry password="$(openssl rand -hex 24)" --entry database=twenty`
`cpln secret create-dictionary --name my-twenty-redis --entry password="$(openssl rand -hex 24)"` (1.4.0)
(Static S3 keys use `cpln secret create-dictionary --name my-twenty-s3-keys --entry STORAGE_S3_ACCESS_KEY_ID=… --entry STORAGE_S3_SECRET_ACCESS_KEY=…`.)

## Availability posture
- **Web tier scales horizontally**; `twenty.replicas > 1` is a supported free-edition shape and requires S3 attachment storage. Default is the proven single-replica shape.
- Measured at `replicas: 2`: rolling upgrade **508/508 HTTP 200**, forced replica stop **198/198 HTTP 200** (full 2/2 recovery 164 s). `maxUnavailableReplicas: "1"` held — never more than one replica out.
- **Worker and bundled Redis stay single-instance.** The worker owns cron registration (and migrations above 1 replica); Twenty accepts only a plain `redis://` URL, so the Sentinel-based redis template cannot be used. A Redis restart stalls background jobs briefly; the UI stays up.
- Database HA is the **opt-in** path (`postgresHA.enabled: true` → 3 Patroni + 3 etcd replicas behind an HAProxy leader endpoint), not the default.

## Troubleshooting / considerations
- **Never assemble a canonical endpoint from parts — the worker rewrites its OWN `CPLN_GLOBAL_ENDPOINT`.** `CPLN_GLOBAL_ENDPOINT` is per-workload, so the worker first advertised its own inbound-less host (`curl` exit 6). An interim fix built `{workload}-$(CPLN_GVC_ALIAS).cpln.app` and broke the SERVER tier too — the canonical form can carry the org alias as a second label and there is **no `CPLN_ORG_ALIAS` variable**. Shipped fix: `/cpln/start.sh` (worker-start secret) `sed`-replaces the workload-name prefix of the worker's own endpoint, then `exec`s `/app/entrypoint.sh yarn worker:prod` so the `DISABLE_*` flags and migration ownership are untouched. Verified live from `/proc/1/environ` at `replicas=1` and cold `replicas=2`: the worker's `SERVER_URL` equals the server's `canonicalEndpoint` byte-for-byte and answers 200.
- **Migrations run in exactly ONE container** (`database:migrate:prod` takes no lock): at `replicas: 1` the server owns them (`DISABLE_DB_MIGRATIONS=false`), at `replicas > 1` the single worker does and every server replica logs `disabled, skipping`. Proven on cold installs in both shapes — never zero migrators, never two.
- **Local storage is a SHARED read-write-many volumeset mounted by both tiers** — an attachment uploaded through the server API is byte-identical when read inside the worker (and the reverse), and survives redeploys of both. An earlier "local attachments are server-only" claim was a maintainer-corrected error. Trade-offs: shared volumes support **expand only, no snapshots**, and live in one location — `s3` is still the production recommendation and is mandatory above 1 replica.
- **`filesystemGroupId: 1000` is not what makes the shared volume work** — the JuiceFS mount root is `drwxrwxrwx root:root`; writes succeed on the 0777 mode. Harmless, but don't reason from it. Also: `status.usedByWorkload` reads `null` even with two workloads mounted — do not use that field to check binding.
- **Boot waits for a live Postgres before migrations (1.3.0).** The app image has no working boot-wait — a bare TCP connect is a no-op on this platform (the mesh sidecar completes the handshake even when nothing listens), so on a fresh install `database:migrate:prod` used to race a not-yet-ready Postgres and the container exited non-zero (a first-boot **exit code 2**), restart-looping until PG happened to be up. Both the server (new `secret-server-start.yaml`) and the worker (`secret-worker-start.yaml`) now run `twenty.dbGate` first: since the Alpine image has no bash (`/dev/tcp` unavailable) but always ships node, the gate drives a **Postgres SSLRequest** in node and requires the one-byte `S`/`N` reply only a live backend gives, before the image entrypoint runs. Capped at 50×5 s (inside the readiness deadline) and exits cleanly for a platform restart if PG never comes — no half-run migration behind an opaque exit. Verified single-region: `waiting for Postgres → Postgres is ready → migrations`, schema complete (69 core tables), zero exit-2.
- **First boot is still slow and logs alarming errors — that part is unchanged and expected.** Single-instance install→ready ≈ 150-240 s while migrations run; every fresh install logs `relation "core.appToken" does not exist` (and siblings) for ~60 s because the migration framework probes for its state tables before creating them, and the readiness probe reports a transient "Health Check Failed" during the migration window (within the 330 s deadline). All healthy — tell users not to abort.
- **The app key is effectively write-once.** Changing `secrets.name` without pointing `secrets.fallbackName` at the old key makes stored OAuth tokens, TOTP secrets and app variables undecryptable. Rotation is proven: pre-rotation session tokens still resolved, zero decrypt errors — but the rollout re-runs boot migrations (351 s to ready). A missing prerequisite secret wedges the deployment and looks broken; uninstall leaves the user's secret intact.
- **On a public endpoint, whoever reaches the URL first owns the CRM** — the first sign-up is a full admin (`canAccessFullAdminPanel: true`). Sign up immediately after install, or install with `publicAccess.enabled: false`.
- **`SERVER_URL` mismatch is the #1 support call** — a custom domain needs `twenty.serverUrl` set explicitly *with* `https://`, or auth callbacks and CORS fail with opaque errors.
- **AWS S3 is keyless-only** — static keys are render-rejected unless `storage.s3.endpoint` is set; MinIO/S3-compatible needs `endpoint` + `auth.secretName` (proven against the in-catalog MinIO template). Note the app writes app-registration assets (`dependencies/package.json`, `generated-sdk-client/*.zip`) into the bucket at boot, before any user upload.
- **The database credentials must be URL-safe** (letters, digits, `-`, `_`) — they are expanded into `PG_DATABASE_URL`. Since 1.4.0 they live only in the user's secret, so the old render-time regex is gone and the constraint is README/wizard prose; a bad character fails at connect time, not at render. The Redis password followed in the same 1.4.0, with the same trade-off.
- **Most settings are not template knobs.** SMTP, AI keys, rate limits and OAuth live in *Settings → Admin Panel → Configuration Variables* (DB-backed, apply in ~15 s). Do not add values knobs for them. Foreign data wrappers ("remote objects") are unavailable — they need upstream's custom Postgres image.
- **Twenty serves TWO GraphQL schemas** — auth/core on `/metadata`, workspace records on `/graphql`; introspection is disabled in this build. Worth knowing before debugging an API call.
- **Volumeset budget:** a default install consumes 3 volumesets (pg, redis, shared storage), the HA variant 4, against a 10-per-GVC cap — relevant when stacking several installs in one GVC.
- **Upstream releases a minor every few days.** 2.26.1 is pinned deliberately; v2.27+ moved sessions to httpOnly cookies, which needs proxy/cookie verification before a bump.
- **1.4.0: the DB credentials became a prerequisite secret (maintainer ruling 2026-10-14, work item 5284).** Rule: when a dependency takes only a credentials-secret NAME, the parent requires the user to create that secret rather than rebuilding it from plaintext values. 1.1.0–1.3.0 kept `postgres.credentials.*` as values (bundled-plumbing exception) and rendered `templates/secret-db.yaml` in both modes, which put the DB password in the Helm release. Now `postgres.credentials` fails at render (`twenty.validateDatabaseSecret`, mirrored in the wizard). The database NAME used to be inlined into `PG_DATABASE_URL` at render; it is now a third secret env var, `PG_DATABASE`, expanded with `$(PG_DATABASE)` like user and password already were. The `twenty.postgres.database`/`.password` helpers and the password regex are gone. **Redis followed in the same 1.4.0** (maintainer 2026-10-16: each datastore gets its OWN dictionary secret): `redis.auth.password` and the chart-created `{release}-twenty-creds` (key `redisPassword`) are gone; Redis (`--requirepass $(REDIS_PASSWORD)`), server and worker (`REDIS_URL` from `$(REDIS_PASSWORD)`) read `cpln://secret/<redis.credentialsSecretName>.password`. The 1.3.x → 1.4.0 upgrade deletes `{release}-twenty-creds`, so the new secret needs another name holding the current password (wizard refuses `{release}-twenty-creds` on that upgrade). Redis rotation = `cpln secret edit` → force-redeploy `-twenty-redis`, `-twenty-worker`, `-twenty` (no password on disk; short interruption). **[UNPROVEN]** live: upgrade with a carried password; the rotation order.
- **Upgrading 1.3.x → 1.4.0 deletes the chart-created DB secret**, because the new chart no longer renders it. The user must create a secret under a NEW name holding the CURRENT credentials (the data dir keeps the password it was initialized with) and point the active mode's `credentialsSecretName` at it; the README snippet uses `RELEASE_NAME-postgres-credentials`, a name 1.3.0 never renders (checked against every 1.3.0 mode/backup render). The wizard enforces the new name with a rule keyed on `context.fromVersion < 1.4.0` (verified headlessly: carried name → 1 error, new name → 0, in single, HA and defaults). Expect the bundled Postgres to restart (it now reads the new secret) and new workload versions to stall ~10 min on `is not allowed to reveal the secret` before clearing on their own (measured on sibling templates). **Not yet live-tested on twenty.**
- **Password rotation:** single-instance — `ALTER ROLE` → `cpln secret edit` → force-redeploy `{release}-postgres` and wait → force-redeploy worker then server. HA — README "Rotating the database password in HA mode": switch the Patroni leader to `-0` first, ALTER the user AND `repl` on `-0`, edit the secret, redeploy (members restart 2→1→0, so `-0` goes last); a plain redeploy can promote a member still on the old password and split the cluster (spike 2026-10-15 on sibling templates).
- **Wizard (1.4.0, first descriptor):** imports postgres 3.4.1 for single mode (pooler excluded + yamlOnly); pg-ha 2.5.0 has no descriptor, so its keys are parent fields in the Database step behind the virtual `dbMode` chooser (single first, the default). Attachment S3 uses a virtual `s3Flavour` (AWS keyless vs S3-compatible static keys). `gvc` limited to 1 location. The `postgresHA.proxy.enabled` mirror can only refuse the key's presence (lint forbids reading an undeclared path), so even an explicit `true` is flagged.
- **History worth knowing:** 1.1.0 adopted postgres 3.4.1 (single-instance credentials moved `postgres.config.*` → `postgres.credentials.*`, MinIO backup keys → `postgres.backup.minio.credentialsSecretName`); 1.2.0 adopted pg-ha 2.5.0 (`postgresHA.postgres.*` removed); 1.2.1 moved HA MinIO keys to `postgresHA.backup.minio.credentialsSecretName`. A stale 1.0.x/1.1.x values file fails with the SUBCHART's removal message (Helm renders `charts/` before `templates/`) — its advice to create a dictionary secret is now correct for twenty too.
- **The DB secret name is org-wide** (a parent cannot template a subchart value, so it cannot carry `.Release.Name`): give each release its own secret.

## 1.4.1 — HA database image override (CVE-2026-103484, work item 5376)
- **`postgresHA.image: controlplanecorporation/patroni-postgres:0.8`** (new key). The vendored `postgres-highly-available` 2.5.0 defaults to `0.7`, which carries pgvector 0.8.0 (CVE-2026-103484: a role that can build an IVFFlat index can run code on the server); `0.8` carries PGDG pgvector 0.8.7 and is otherwise the same image. Maintainer decision 2026-10-27: override the image in the parent and keep the vendored subchart version; moving to `postgres-highly-available` 2.8.1 is a later batch.
- **`twenty.validatePostgresHAImage`** (HA mode only) refuses `controlplanecorporation/patroni-postgres` tags `0.1`-`0.7` (with or without `docker.io/`) using `pg-ha.validateImage`'s matching, and also an emptied `postgresHA.image`, because the subchart would then fall back to its `0.7` default. Mirrored by the wizard rule on the new `postgresHA.image` field (Database step, HA group).
- **Single-instance mode is unaffected**: it runs the official `postgres:18`, which ships no pgvector. Twenty does not create the `vector` extension (grep of the chart, plus upstream source), so the README tells only users who created it themselves to run `ALTER EXTENSION vector UPDATE;`.
- **The upgrade rolls the Patroni members one at a time** (image change on the stateful workload, with a leader handover). [UNPROVEN] on twenty itself: not deployed in this change; the E2E suite onboarded in 1.4.1 (`twenty/tests/`, HA baseline, `upgradeFrom: 1.4.0`) proves the upgrade and the `pgvector-0-8-7-available` check in CI.
