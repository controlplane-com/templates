# Unleash — Maintainer Briefing

## What it is
- Open-source feature-flag server (toggle features on/off, gradual rollouts, A/B tests) with an admin web UI; all state in PostgreSQL.
- License: v8 Docker image stays Apache-2.0 (permissive), but the v8 source moved to AGPL (a strong open-source license: anyone offering a modified version as a network service must share their changes). We ship the unmodified image — see spec Open Question 1.

## Common use cases
- Roll a feature out to 10% of users, then ramp up, without redeploying.
- Kill switch: instantly disable a broken feature in production.
- A/B testing and per-user/per-segment targeting via SDKs in the user's own apps.
- Separate `development` / `production` flag states (the only 2 environments in the free edition).

## Architecture on cpln
| Resource | Purpose |
|---|---|
| `{release}-unleash` workload (standard, :4242 http) | Server: admin UI + Admin/Client/Frontend APIs on one port |
| user's `admin.secretName` secret (dictionary, **prerequisite**) | First-boot admin `username`/`password` — user-created since 1.1.0, never by the chart |
| user's `apiTokens.secretName` secret (optional, prerequisite) | First-boot SDK tokens — user-created dictionary secret with keys `backend` + `frontend`; template only references it by name |
| `{release}-unleash-start` secret | Boot script — sets the public URL at runtime |
| identity + policy | Reveal (read) access on exactly the secrets above + the user's DB credentials secret, by name |
| postgresHA (default) or postgres subchart | The database — holds every flag, user, and token |
| DB credentials secret (dictionary, **user-created** since 1.5.0) | `username`/`password`/`database` — named by `postgresHA.config.credentialsSecretName` (HA) or `postgres.config.credentialsSecretName` (single); the active subchart initializes from it and Unleash's `DATABASE_NAME`/`USERNAME`/`PASSWORD` read it. pg-ha's `{release}-postgres-config` holds only backup bucket/region, and only when HA backups are on |

- Fully stateless server: no volumeset; `replicas: 2+` scales it behind the load balancer (default 1).
- Dual database mode like n8n/metabase/temporal: HA Postgres default, single Postgres for dev; exactly one must be enabled.

## Key knobs
`image` · `replicas` (1 default, 2+ = HA) · `admin.secretName` (prerequisite dictionary secret: `username` + `password`; first boot only) · `apiTokens.secretName` (first boot only; prerequisite dictionary secret with keys `backend`/`frontend`, token format `project:environment.secret`) · `publicAccess.enabled` (default true) · `internalAccess.type` · `postgresHA.config.credentialsSecretName` / `postgres.config.credentialsSecretName` (both default `my-unleash-db-credentials`; REQUIRED prerequisite dictionary secret for the mode in use, **1.5.0+**; must exist BEFORE install) · backups on either store (MinIO keys via `*.backup.minio.credentialsSecretName` on both, HA since 1.3.1)

## Troubleshooting / considerations
- **Workload wedged with ZERO log lines** → a prerequisite secret (admin, DB credentials, or, if named, the API-token secret) does not exist. The container never starts, so `cpln logs` is empty; the diagnostic is `status.versions[].message` from `cpln workload get-deployments … -o yaml` (**not** plain `get`). Self-heals in ~5.5–10.5 min once created, or force a redeployment (~90 s).
- **First-boot-only seeds:** the admin password and `apiTokens` are written to the database once. Editing the secrets and upgrading does nothing — change the password in the UI; create new tokens in the UI. A full reset requires uninstall (deletes the DB volume) + reinstall.
- **No credential passes through helm:** `apiTokens.secretName` (default empty = no seeding), since 1.1.0 `admin.secretName`, and since 1.5.0 the DB credentials secret only NAME secrets the user pre-creates. The admin move follows the 2026-08-07 ruling — it guards a public human-facing login; `fail` guards name the replacement for the removed `admin.username`/`admin.password`, with no shims.
- **Backend vs frontend token confusion** is the #1 SDK support call: backend tokens (server-side SDKs, `/api/client`) must stay secret; frontend tokens (`/api/frontend`) are safe to embed in browsers. A 401 usually means the wrong token type or wrong environment in the token string.
- **Only 2 environments in the free edition** (`development`, `production`). SSO, role-based access control (per-user permission tiers), multiple projects, change requests, and audit logs are all paid-Enterprise — never tell a user these are one config flag away.
- **Public URL links:** password-reset/invite links use `UNLEASH_URL`, derived at boot from the canonical endpoint. If links look wrong after toggling `publicAccess`, restart the workload so the boot script re-derives it.
- **DB connections:** each replica opens at most 4 Postgres connections (upstream default), so replica count is never a connection-limit concern at sane scale.
- **v8 needs PostgreSQL 15+** — both our dependency charts qualify (pg-ha = PG 17, postgres = PG 18); relevant if external-DB support is added later.
- **HA-mode first boot takes ~5–7 min at any replica count** (test-proven): transient `Failed to migrate db` errors while the database cluster starts are expected and self-heal; there is NO replicas-specific first-boot race (fresh install at 2 converged unaided, zero migration conflicts — never advise install-at-1-then-scale).
- **1.5.0: the DB credentials became a prerequisite secret (maintainer ruling 2026-10-14, work item 5284).** Rule: when a dependency requires a pre-existing credential secret, the parent requires it too, rather than rebuilding it from plaintext values. 1.2.0–1.4.0 kept `postgres.credentials.*` as values under the bundled-plumbing exception and rendered the secret itself (`secret-db.yaml`, now deleted) in both modes; that put the DB password in the Helm release. `postgres.credentials` now fails at render (`unleash.validateDatabaseSecret`, mirrored in the wizard). No render-time check on the plaintext values existed, so nothing else moved; Unleash takes the password as a discrete env var (no URL), so no character restriction applies.
- **Upgrading 1.4.0 → 1.5.0 deletes the chart-created DB secret**, because the new chart no longer renders it. The user must create a secret under a NEW name holding the CURRENT credentials (the data dir keeps the password it was initialized with) and point the active mode's `credentialsSecretName` at it. The wizard enforces the new name with an `oldSelf` rule. Expect the new workload version to stall ~10 min on `is not allowed to reveal the secret` (authorization edge cache, measured on gitea 1.3.0) before clearing on its own. Not yet live-tested on unleash.
- **Both name knobs exist because a parent cannot template a subchart value**: each subchart reads its own `config.credentialsSecretName`; `unleash.postgres.secret.name` picks the active one. Only the active mode's key matters.
- **Older upgraders get the subchart's own removal errors** (`postgres.config.username` from postgres 3.4.x, the `postgres` block from pg-ha 2.5.0); their advice — create a dictionary secret — is now correct for unleash too.
- **Wizard (1.5.0, first descriptor):** imports postgres 3.4.1 (when single mode; pooler excluded); pg-ha 2.5.0 has no descriptor, so its keys are parent fields in the Database step (two toggle sections, exactly-one rule). `gvc` limited to 1 location (both DBs are single-location).
- **MinIO backup keys are a prerequisite dictionary secret on both paths** (`accessKey`/`secretKey`) — `postgres.backup.minio.credentialsSecretName` since postgres 3.4.0 (unleash 1.2.0), `postgresHA.backup.minio.credentialsSecretName` since unleash 1.3.1 (1.3.0 still shipped the inline keys pg-ha 2.5.0 refuses).
- **Availability numbers (test-proven):** rolling redeploy @2 replicas = 55/55 polls served; replica kill @2 = 30/30; even a single-replica upgrade served 63/63 (the platform surges the replacement before stopping the old one).
- **HA password rotation must also update the `repl` role (measured on listmonk 1.6.0, 2026-10-14).** postgres-highly-available 2.5.0 uses the same secret password for its replication user `repl`; after `ALTER ROLE <user>` + secret edit + redeploy, the standbys failed with `password authentication failed for user "repl"` while the app kept working on the leader. `ALTER ROLE repl PASSWORD '<new>'` on the leader restored streaming in ~12 s. README and wizard help say so.
- **HA rotation ORDER matters (spike 2026-10-15, postgres-highly-available 2.5.0, 3/3 pass).** `ALTER` + secret edit + force-redeploy of `-postgres-ha` is NOT safe on its own: the platform restarts members highest ordinal first (2→1→0, observed 5/5, undocumented) and the chart's preStop calls `/switchover` with no candidate, so the leader can hand off to a member still on the OLD password. Measured: a diverged timeline that HAProxy routed clients to (spike), and on chatwoot a replica stuck `forked off` for 19 min while the leader streamed ~16 GB/min to it (~$30 egress, single location). Safe order (README section): switch the leader to `-0` first, ALTER user + `repl` on `-0`, edit the secret, redeploy — `-0` restarts last. Recovery: `POST /reinitialize {"force":true}` on the stuck member. Also: Patroni's DCS config keeps the INSTALL-time password readable unauthenticated at `:8008/config` (survives rotation) — README step 7 PATCHes it out; chart fix + preStop candidate hardening tracked on 5284.
- **1.5.1: HA database image override for CVE-2026-103484 (work item 5376).** The vendored postgres-highly-available 2.5.0 defaults to `patroni-postgres:0.7` (pgvector 0.8.0); 1.5.1 sets `postgresHA.image: controlplanecorporation/patroni-postgres:0.8` (pgvector 0.8.7) and keeps the vendored 2.5.0, because pg-ha 2.8.1 was not published yet. `unleash.validatePostgresHAImage` refuses `patroni-postgres` tags 0.1–0.7 when HA is on (same matching as pg-ha 2.8.1's `pg-ha.validateImage`), mirrored in the wizard's HA section. Unleash does not use pgvector, so the risk was only to users who created the extension themselves; the upgrade is a Patroni rolling restart (highest ordinal first, preStop switchover). Single-instance mode is unaffected. Remove the override when unleash moves to pg-ha 2.8.1+.
